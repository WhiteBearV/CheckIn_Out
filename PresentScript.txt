โดยทั้งสามคนช่วยกันออกแบบและพัฒนามาตลอด 2 เดือนนี้

ชื่อโปรเจกต์คือ "Face Attendance System" หรือระบบลงเวลาด้วยใบหน้า
ซึ่งผมจะค่อย ๆ เล่าให้ฟังตั้งแต่ที่มาของปัญหา สิ่งที่เราสร้าง
และโดยเฉพาะอย่างยิ่งปัญหาที่เจอระหว่างทาง ซึ่งน่าจะเป็นส่วนที่
ได้เรียนรู้มากที่สุดครับ

หน้า 2 — Project Overview
────────────────────────────────────────────────────────────────

ก่อนอื่นขอเล่าว่าทำไมถึงต้องสร้างระบบนี้ขึ้นมาครับ

ระบบลงเวลาแบบเดิมไม่ว่าจะเป็นบัตรแตะ สแกนนิ้ว หรือเซ็นชื่อ
ล้วนมีจุดอ่อนร่วมกันอยู่ข้อหนึ่งคือ ต้องสัมผัส และต้องพกสิ่งของ
บัตรลืมทิ้งไว้บ้านก็เข้าไม่ได้ สแกนนิ้วในช่วงอากาศหนาวหรือมือเปียก
ก็อ่านค่าไม่ได้ และที่สำคัญ ยืมบัตรกันแตะแทนได้ง่ายมาก

เราเลยอยากสร้างระบบที่ใช้สิ่งที่ติดตัวทุกคนมาตลอด
นั่นก็คือใบหน้าของตัวเองครับ

แนวคิดง่ายมากคือ พนักงานแค่เดินเข้าใกล้กล้อง ระบบจะจำหน้า
และบันทึกเวลาให้เองโดยอัตโนมัติ ไม่ต้องทำอะไรเพิ่มเติม

ในการสร้างระบบนี้เราใช้เทคโนโลยีหลัก 4 ตัวครับ

ตัวแรกคือ InsightFace ที่ใช้โมเดล ArcFace สร้าง face embedding
ขนาด 512 มิติ ซึ่งเหมาะมากกับคนเอเชียเพราะ trained มาบนชุดข้อมูล
ที่หลากหลายกว่า library ทั่วไป

ตัวที่สองคือ MediaPipe ใช้ตรวจจับจุดบนใบหน้าและมือ
เพื่อทดสอบว่าคนที่ยืนอยู่หน้ากล้องเป็นคนจริงหรือเปล่า
ไม่ใช่แค่รูปถ่ายหรือวิดีโอที่ใครเอามาโกง

ตัวที่สามคือ FastAPI ทำหน้าที่เป็น backend สำหรับรับและส่งข้อมูล
การลงเวลาระหว่าง AI กับฐานข้อมูล

และตัวสุดท้ายคือ Vue 3 ซึ่งเป็น frontend สำหรับ Dashboard
ที่ admin ใช้ดูข้อมูลการเข้างานแบบเรียลไทม์ครับ

ระบบนี้ไม่ได้สมบูรณ์ตั้งแต่ต้นครับ เราผ่านการ iterate มากกว่า 10 เวอร์ชัน

เริ่มต้น เวอร์ชัน 1 ถึง 4 เป็นช่วงวางรากฐานครับ
เราใช้ OpenCV กับ library face_recognition ซึ่งตอนนั้นเป็นตัวเลือก
ที่ง่ายและเริ่มต้นได้เร็ว ข้อมูลเก็บใน SQLite ที่เป็น local file
ตอนนั้นระบบทำงานได้ แต่ความแม่นยำยังไม่ดีพอ
โดยเฉพาะกับคนเอเชีย ซึ่งจะพูดถึงละเอียดในหน้า Problem ครับ

เวอร์ชัน 5 คือจุดเปลี่ยนครั้งใหญ่ที่สุด
เราตัดสินใจ migrate เปลี่ยน face recognition engine ทั้งหมด
มาใช้ InsightFace กับ ArcFace แทน
ผลลัพธ์คือ accuracy กระโดดขึ้นมาเกือบ 95% ทันทีครับ

เวอร์ชัน 6 และ 7 เป็นช่วงที่ระบบเริ่มโตขึ้น
เราย้าย database ให้รองรับข้อมูลมากขึ้น แก้ปัญหา GPU
และเพิ่ม Anti-Spoofing เข้ามาครบ 6 ชั้น รวมถึงรองรับกล้อง IP ด้วย

เวอร์ชัน 8 ถึง 9 เน้นเรื่อง integration กับระบบภายนอก
มีการดึงข้อมูลบุคลากรจาก External API แทนที่จะ maintain ข้อมูลแยก
และเพิ่ม security hardening หลายส่วน

เวอร์ชัน 10 เป็นเวอร์ชันที่ระบบพร้อม deploy จริงครับ
รองรับหลายกล้องพร้อมกัน มี Web Dashboard แสดงผลเรียลไทม์
และมี GUI สำหรับ admin จัดการกล้องได้โดยไม่ต้องแก้ config ไฟล์

และเวอร์ชัน 11 ล่าสุดเป็นการแก้บั๊กที่ซ่อนอยู่ครับ
โดยเฉพาะ Race Condition ตอนหลายกล้องทำงานพร้อมกัน
ซึ่งเป็นบั๊กที่ reproduce ยากมาก เพราะเกิดแบบสุ่มตามจังหวะ timing


────────────────────────────────────────────────────────────────
หน้า 4 — Anti-Spoofing Pipeline
────────────────────────────────────────────────────────────────

ส่วนที่อยากพูดถึงเป็นพิเศษคือ Anti-Spoofing ครับ
เพราะมันคือส่วนที่ทำให้ระบบนี้ต่างจากแค่ "จดจำใบหน้า" ทั่วไป

ปัญหาของ face recognition ระบบทั่วไปคือ ถ้าเอารูปถ่ายของคนในระบบ
มาถือหน้ากล้อง มันก็จำได้เหมือนกันครับ ซึ่งนั่นทำให้ระบบไม่ปลอดภัยเลย
เราเลยต้องออกแบบ pipeline ตรวจสอบว่าคนที่ยืนอยู่หน้ากล้อง
เป็น "คนจริงที่มีชีวิต" ไม่ใช่รูป วิดีโอ หรือหน้ากาก

เราแบ่งออกเป็น 6 ชั้นครับ โดยแต่ละชั้นออกแบบมาเพื่อจัดการกับการโกงคนละประเภท

ชั้นที่ 1 ตรวจความลึก 3 มิติจาก landmark 68 จุดบนใบหน้า
รูปถ่าย 2 มิติจะมี depth distribution ที่แบนกว่าใบหน้าจริงอย่างเห็นได้ชัดครับ

ชั้นที่ 2 ตรวจการเคลื่อนไหวระดับ micro-motion
คนจริงที่ถือมืออยู่เฉย ๆ ยังมีการสั่นเล็กน้อยจากการหายใจ
รูปนิ่งไม่มีครับ

ชั้นที่ 3 ตรวจการกะพริบตา โดยวัดจากค่า Eye Aspect Ratio
ซึ่งจะเปลี่ยนเมื่อตากะพริบ รูปถ่ายมักมีตาเปิดค้าง ผ่านได้ยากมาก

ชั้นที่ 4 วิเคราะห์ texture ของผิวหนัง
เมื่อแสดงใบหน้าผ่านหน้าจอ จะมีรอย LCD pixel pattern และ Moiré effect
ที่อัลกอริทึม LBP กับ Laplacian จับได้

ชั้นที่ 5 คือ Finger Challenge ซึ่งเป็น interactive test ครับ
ระบบจะสุ่มถามให้ชูนิ้วจำนวนที่กำหนด สองชุดต่างกัน
รูปหรือวิดีโอที่เตรียมมาล่วงหน้าผ่านไม่ได้แน่นอน

ชั้นสุดท้ายที่ 6 คือ MiniFASNet ซึ่งเป็น deep learning model
ที่ trained มาเพื่อตรวจ spoof โดยเฉพาะ มองทั้งภาพรวมของใบหน้า
แล้วให้ score ออกมาว่าเป็น real หรือ fake

เหตุที่ต้องมี 6 ชั้นแทนที่จะพึ่งตัวเดียวก็เพราะ
แต่ละวิธีมีจุดอ่อนของตัวเองครับ การรวมหลายวิธีทำให้โกงยากขึ้นมากเพราะ
ต้องผ่านทุกชั้นพร้อมกันถึงจะเข้าระบบได้

หน้า 5 — System Architecture
────────────────────────────────────────────────────────────────

ในแง่ architecture ระบบถูกแยกออกเป็น 3 โปรเซสที่ทำงานอิสระจากกันครับ

เหตุผลที่ไม่รวมทุกอย่างไว้ที่เดียวก็เพราะแต่ละส่วนมี nature ต่างกัน
กล้องต้องการ latency ต่ำมาก ส่วน web dashboard รับ request ได้หลาย ๆ คน
พร้อมกัน ถ้าตัวใดตัวหนึ่งหนัก มันจะไม่ฉุดส่วนอื่นลงด้วยครับ

โปรเซสแรกคือ main.py ซึ่งเป็น core ของระบบ
มันจะ spawn thread แยกสำหรับแต่ละกล้อง ทำให้กล้อง 3 ตัว
ทำงานพร้อมกันได้โดยไม่รบกวนกัน แต่ละ thread ก็จะ
detect หน้า → สร้าง embedding → เปรียบเทียบ → ทำ anti-spoofing วนซ้ำ

โปรเซสที่สองคือ api.py บนพอร์ต 8000 ทำหน้าที่เป็น REST API
รับ check-in check-out จาก main.py และให้ข้อมูลกับ dashboard ครับ

โปรเซสที่สามคือ stream_server.py บนพอร์ต 8001
ส่ง video stream ผ่าน MJPEG ไปให้ web UI
เพื่อให้ admin ดูภาพจากกล้องได้แบบ live ผ่านบราวเซอร์

การตั้งค่าทั้งหมดอยู่ใน cameras.json ซึ่งเราออกแบบให้แก้ได้จาก UI
โดยไม่ต้อง restart process และ credential ต่าง ๆ เก็บแยกใน .env
เพื่อไม่ให้หลุดเข้า version control ครับ

ซึ่งสำคัญมากในการใช้งานจริงที่ admin อาจไม่ใช่คนที่เขียนโค้ดครับ


────────────────────────────────────────────────────────────────
หน้า 7 — Docker
────────────────────────────────────────────────────────────────

ระบบทั้งหมด package ด้วย Docker ครับ

เหตุผลหลักที่เลือก Docker คือ dependency ของโปรเจกต์นี้ซับซ้อนมาก
มีทั้ง CUDA, cuDNN, ONNX Runtime, OpenCV, MediaPipe ที่ต้องการ version
ที่เข้ากันพอดี ถ้าติดตั้งบน host machine ตรง ๆ มีโอกาสสูงมากที่
version จะ conflict กับ package อื่นที่มีอยู่แล้วในเครื่อง

Docker ทำให้เราควบคุม environment ได้ทั้งหมดครับ
machine ไหนก็ run ได้เหมือนกัน ไม่มี "works on my machine" อีกต่อไป

แต่ละ service แยก container กัน ทำให้ถ้า AI process หนักหรือ crash
มันไม่ดึง dashboard ลงไปด้วย สามารถ restart เฉพาะ service ที่มีปัญหา
ได้อย่างอิสระ และ scale ได้ทีหลังถ้าต้องการครับ


────────────────────────────────────────────────────────────────
หน้า 8 — Program Flow
────────────────────────────────────────────────────────────────

ลองเดิน walk-through ว่าตั้งแต่เปิดโปรแกรมจนกล้องบันทึกเวลาสำเร็จ
มีอะไรเกิดขึ้นบ้างครับ

ตอน startup ระบบโหลด config จาก cameras.json ก่อน
แล้ว resolve ตัวแปรจาก .env เพื่อไม่ให้ credential แข็งอยู่ใน code
จากนั้น spawn thread แยกสำหรับแต่ละกล้องที่ config ไว้

ใน thread ของแต่ละกล้อง จะมีลูปทำงานตลอดเวลาครับ
โดยในแต่ละ frame ระบบจะ detect ก่อนว่ามีใบหน้าไหม
ถ้ามี จะส่งไปให้ ArcFace สร้าง embedding ขนาด 512 มิติ
แล้วเอาไปเทียบกับ database ด้วย Cosine Similarity
ค่าที่ได้จะบอกว่าใบหน้านี้ใกล้เคียงกับใครมากที่สุด
ถ้าผ่านเกณฑ์ threshold ก็ถือว่าจำได้ครับ

เมื่อจำได้แล้ว จะยังไม่ check-in ทันทีนะครับ
ต้องผ่าน Anti-Spoofing Pipeline ก่อน ซึ่งใช้เวลาสักครู่
เพราะต้องรอ blink detection, finger challenge และ MiniFASNet ครบ
ถ้าผ่านครบทุกชั้นแล้ว ระบบถึงจะ POST ไปยัง API เพื่อบันทึก check-in
พร้อม snapshot รูปและข้อมูลบุคลากรครับ

ส่วน check-out ไม่ต้องทำอะไรเลย ระบบจะ check-out ให้อัตโนมัติ
เมื่อถึงเวลา CHECKOUT_TIME ที่กำหนดไว้ใน config ครับ


────────────────────────────────────────────────────────────────
หน้า 9 — Problem 1: Screen Border False Positive จากกล้อง IP RTSP
────────────────────────────────────────────────────────────────

ตอนนี้ขอเล่าปัญหาที่เจอจริงระหว่างพัฒนาครับ
ซึ่งส่วนตัวคิดว่าเป็นส่วนที่ได้เรียนรู้เยอะที่สุด

ปัญหาแรกเกิดขึ้นตอนที่เราย้ายจากกล้อง USB มาใช้กล้อง IP ผ่าน RTSP
ทุกอย่างดูดีบนกล้อง USB ครับ แต่พอเปลี่ยนกล้อง ระบบกลับปฏิเสธทุกคนหมด
log บอกว่าเป็น "screen" ตลอด ทั้งที่คนยืนอยู่จริง ๆ

ตอนแรกนึกว่าเป็นเรื่องการตั้งค่า threshold ครับ เลยลองปรับค่าต่าง ๆ
แต่ไม่ได้ผล FFT score เป็น 0.000 ตลอดเวลาเลย ซึ่งผิดปกติมาก

พอลงไป debug จริง ๆ เจอสาเหตุสามอย่างที่ซ้อนกันอยู่ครับ

อย่างแรกคือ H.264 codec ที่กล้อง IP ใช้ compress วิดีโอ RTSP
มันสร้าง DCT block artifact ขึ้นมาในภาพ
ซึ่ง FFT algorithm ของเราอ่านเป็น frequency pattern เหมือน pixel grid ของ LCD
นั่นหมายความว่า codec ของกล้อง IP ทำให้ภาพ "ดูเหมือนหน้าจอ" ในสายตาของโค้ดครับ

อย่างที่สองคือ กล้อง IP ใช้เลนส์ wide-angle ซึ่ง field of view กว้างมาก
ขอบโต๊ะ ขอบประตู หรือกรอบหน้าต่างที่อยู่พื้นหลัง
ถูก algorithm ตีความว่าเป็นขอบจอครับ

อย่างที่สามคือ เจอบั๊กใน code ด้วย ตอน refactor ครั้งก่อน
มีการลบ early return ออกโดยไม่ตั้งใจ ทำให้ logic การตรวจ screen
ไม่มีทางออก false ได้เลยในบางกรณีครับ

วิธีแก้คือ re-calibrate สูตร FFT ใหม่ ลดน้ำหนักของ peak_rate
เพิ่ม time-based confirmation คือต้องตรวจซ้ำ 3 วินาทีก่อน fail
และจำกัดพื้นที่ที่ตรวจให้อยู่แค่บริเวณใบหน้า
ไม่ให้ background เข้ามารบกวนครับ

บทเรียนจากเรื่องนี้คือ algorithm ที่ทำงานดีบน hardware ชุดหนึ่ง
อาจพังทันทีเมื่อเปลี่ยน input source ครับ
ต้องทดสอบบน environment จริงเสมอ

หน้า 10 — Problem 2: GPU Inference ไม่ทำงาน
────────────────────────────────────────────────────────────────

ปัญหาที่สองน่าหงุดหงิดกว่าครับ เพราะ GPU ไม่ทำงาน
แต่ระบบไม่บอกว่าพังนะ มัน fallback ไป CPU เงียบ ๆ เฉย ๆ
ทำให้เราไม่รู้ว่ามีปัญหาอยู่จนกระทั่ง FPS ตก 4-5 เท่าตอนมีคนเดินหน้ากล้อง

อาการมีสองแบบครับ แบบแรกคือ log มี warning ขึ้นมาว่า
CUDNN_STATUS_SUBLIBRARY_LOADING_FAILED แล้วก็ยังรันต่อ
แต่ช้ามาก แบบที่สองร้ายกว่าคือ container crash ทันทีด้วย exit code -11
ซึ่งคือ SIGSEGV หรือ segmentation fault ไม่มี traceback เลย
debug ยากมากครับ

พอ investigate ลึก ๆ เจอว่ามีสาเหตุซ้อนกันสามชั้นเลย

ชั้นแรกคือ software incompatibility ครับ
cuDNN 9.10.2 ที่ติดตั้งอยู่ใหม่เกินไป ยังไม่ compatible กับ ONNX Runtime ที่ใช้
บวกกับ numpy 2.x และ protobuf 7.x ที่มี ABI break
ทำให้ library คุยกันไม่รู้เรื่อง

ชั้นที่สองคือ infrastructure ครับ container ไม่ได้ mount GPU เข้ามาด้วย
แต่เราติดตั้ง onnxruntime-gpu ไว้ใน image
เลยได้ GPU version แต่ไม่มี GPU ให้ใช้

ชั้นที่สามคือ race condition ครับ ตอน container เริ่มต้น
thread สองตัวพยายาม download model พร้อมกันในโฟลเดอร์เดียว
ทำให้ไฟล์ model corrupt กลายเป็น segfault ตอนโหลด

วิธีแก้คือ pin version ทุกอย่างใน requirements.txt ให้ชัดเจน
ใส่ GPU config ใน docker-compose ให้ครบ ทั้ง runtime: nvidia
และ NVIDIA_VISIBLE_DEVICES=all และเพิ่ม model warm-up ใน main thread
ก่อน spawn worker thread เพื่อให้ model โหลดแล้วเสร็จก่อนใครจะใช้ครับ

และเพิ่ม defensive code ที่ log ว่าระบบใช้ provider อะไรอยู่
เพื่อให้รู้ทันทีตอน startup ว่า GPU ทำงานหรือเปล่า แทนที่จะรู้ตอน FPS ตกครับ

หน้า 11 — Problem 3: ArcFace Migration (v5)
────────────────────────────────────────────────────────────────

ปัญหาที่สามนี้จริง ๆ เกิดก่อนสองปัญหาที่พูดมาครับ
เป็นปัญหาตั้งแต่ช่วงต้นของโปรเจกต์ที่ทำให้ต้อง rethink ทิศทางทั้งหมด

ตอนเริ่มต้น เราใช้ library ชื่อ face_recognition ซึ่งเป็น wrapper ของ dlib
เป็น library ที่ง่าย เริ่มต้นได้เร็ว มี tutorial เยอะมาก
แต่ตอนทดสอบกับ dataset คนไทยจริง ๆ มีการจำสลับตัวกันบ่อยมากครับ
accuracy อยู่แค่ 75% และ FPS ก็แค่ 6-8 เท่านั้น

พอ investigate เจอว่าสาเหตุมาจาก training bias ครับ
model ที่อยู่ข้างใต้ dlib ถูก train มาบนชุดข้อมูลที่มีคนผิวขาวเป็นหลัก
ทำให้ discriminative power กับใบหน้าคนเอเชียต่ำกว่ามาก
เพิ่มเติมคือ embedding มีแค่ 128 มิติ ซึ่งน้อยเกินไปสำหรับการแยกแยะ
คนที่มีหน้าคล้ายกัน และยังใช้ Euclidean distance ที่ไม่เหมาะกับ high-dimensional vector
และที่สำคัญคือรองรับเฉพาะ CPU ครับ

เราเลยตัดสินใจ migrate ทั้งหมดไปใช้ InsightFace buffalo_l
ที่มี ArcFace บน ResNet50 สร้าง embedding 512 มิติ
trained บน dataset ที่หลากหลายและมีคนเอเชียมากกว่า
เปลี่ยนมาใช้ Cosine Similarity แทน และรัน inference บน GPU ได้

ต้อง re-encode รูปถ่ายทั้งหมดใหม่ด้วย encode_faces_arcface.py
และ re-tune threshold ต่าง ๆ ใหม่หมดเพราะ scale ของ embedding เปลี่ยนไปครับ

ผลลัพธ์หลัง migrate accuracy กระโดดจาก 75% เป็น 95%
FPS จาก 6-8 เป็น 22-25 และรองรับหลายกล้องพร้อมกันได้แล้วครับ

บทเรียนคือ เลือก library ต้องดู use case จริงด้วย
ไม่ใช่แค่ใช้ง่ายหรือมี tutorial เยอะ โดยเฉพาะถ้า target user ไม่ตรงกับ dataset ที่ train มาครับ

หน้า 12 — Problem 4: ระบบเวลาไม่ตรง และการตั้งค่าไม่คงอยู่ถาวร
────────────────────────────────────────────────────────────────

ปัญหาสุดท้ายนี้ดูเล็กแต่ impact ใหญ่มากครับ
เพราะระบบบันทึกเวลาที่เวลาไม่ตรงใช้ประโยชน์ไม่ได้เลย

อาการแรกที่เจอคือ dashboard แสดงเวลาช้ากว่าจริง 7 ชั่วโมงครับ
คนเดินเข้างาน 8 โมงเช้า แต่ log บอก 1 ทุ่ม
นั่นเพราะ Docker container ใช้เวลา UTC โดย default
ไม่ได้รับค่า timezone จาก host machine

อาการที่สองคือทุกครั้งที่ docker compose down แล้ว up ใหม่
การตั้งค่าทั้งหมดที่เคยแก้ไว้หายหมดเลยครับ ต้องตั้งใหม่ทุกครั้ง
เพราะเราทำการตั้งค่าใน runtime ไม่ได้ฝังไว้ใน image

วิธีแก้เรื่อง timezone คือเพิ่ม TZ=Asia/Bangkok ใน docker-compose
และฝังการติดตั้ง tzdata ไว้ใน Dockerfile ตั้งแต่ตอน build
พร้อม symlink ไปยัง /etc/localtime ให้เรียบร้อยครับ

วิธีแก้เรื่อง config หายคือ lock version library ทุกตัวใน requirements.txt
เช่น numpy==1.26.4 ให้ชัดเจน เพื่อป้องกันไม่ให้ auto-update
ดึง version ใหม่มาทำลาย behavior ที่ตั้งไว้ครับ

บทเรียนจากเรื่องนี้คือ container ไม่ได้รับ assumption จาก host
ทุกอย่างต้องตั้งค่าไว้ใน image หรือ config อย่างชัดเจนครับ
อะไรที่ทำงานได้บนเครื่องตัวเองอาจพังทันทีใน container ถ้าไม่ระวัง

หน้า 13–17 — สรุป / ถาม-ตอบ (ปรับตามสไลด์จริง)
────────────────────────────────────────────────────────────────

ขอสรุปภาพรวมของโปรเจกต์นี้ครับ

ตลอด 2 เดือนที่ผ่านมา เราพัฒนาระบบจากศูนย์ผ่านมากกว่า 10 เวอร์ชัน
จนได้ระบบที่มี accuracy 95%, รองรับหลายกล้องพร้อมกัน
มี Anti-Spoofing 6 ชั้น และ Web Dashboard สำหรับ admin ใช้งานได้จริงครับ

สิ่งที่ได้เรียนรู้มากที่สุดจากโปรเจกต์นี้ไม่ใช่แค่ตัว AI algorithm ครับ
แต่เป็นเรื่อง engineering รอบข้าง ทั้ง Docker, GPU driver, concurrency
และการ debug ระบบที่มีหลาย layer ซ้อนกัน
ซึ่งทักษะเหล่านี้ไม่ได้มีในหนังสือเรียนตรง ๆ แต่ได้จากการลองแล้วเจอปัญหาจริงครับ

ทุกปัญหาที่เล่ามา แต่ละอย่างใช้เวลา debug นานมาก
แต่ก็ทำให้เข้าใจระบบลึกขึ้นมากทุกครั้งที่แก้ได้

ขอบคุณทุกท่านที่รับฟังครับ ยินดีตอบคำถามครับ
