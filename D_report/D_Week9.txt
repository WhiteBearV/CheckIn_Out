■ งานที่ดำเนินการในวันนี้
────────────────────────────────────────────────────────────────────────

1. ปรับ Architecture และตั้งค่า Network Paths บน Raspberry Pi 4 (ช่วงเช้า)
   ─────────────────────────────────────────────────────────────────
   ปรับแผน MVP Channel Bonding จากแผนเดิมที่ใช้ M8550 2 ตัวผ่าน USB-Eth
   เป็น WiFi hotspot (iPhone) + eth0 (M8550 #1) เพื่อให้สามารถทดสอบ
   Channel Bonding จริงได้ด้วยอุปกรณ์ที่มีอยู่

   ขั้นตอนการดำเนินการ:
     1. ตั้งค่า 2 Network Paths บน Pi 4
        - Path 1 : wlan0 (WiFi hotspot iPhone) — IP 172.20.10.2, Gateway 172.20.10.1
        - Path 2 : eth0 (M8550 5G)            — IP 192.168.1.4,  Gateway 192.168.1.1
        - ตรวจสอบ Public IP ของแต่ละ path ออก Internet คนละทางจริง

     2. ตั้งค่า Policy Routing
        - สร้างไฟล์ /etc/iproute2/rt_tables พร้อม default content
          (ไม่มีมาก่อนใน Pi OS minimal)
        - สร้าง routing table wifi (100) และ m8550 (200)
        - กำหนด rules: source IP → routing table ที่เหมาะสม
        - ทดสอบยืนยัน Public IP ออกคนละทางจริงด้วย curl --interface

2. ติดตั้งและทดสอบ Glorytun Client บน Pi 4 (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   ค้นหา syntax ที่ถูกต้องของ Glorytun version 0.3.4-51-g32267e8
   และทดสอบ handshake กับ Server ที่มี Public IP จริง

   ขั้นตอนการดำเนินการ:
     1. ค้นพบ syntax ของ Glorytun 0.3.4 ที่ถูกต้อง
        - เอกสาร MVP เก่าระบุ glorytun connect → ไม่มีใน version นี้
        - syntax ที่ใช้ได้จริง: glorytun bind ... from port 0 to addr ... port ...
        - ศึกษา glorytun path สำหรับเพิ่ม/จัดการ multi-path

     2. ตั้งค่า Tunnel
        - สร้าง interface gt0 พร้อม Tunnel IP 10.255.255.2/30
        - เพิ่ม 2 paths: wlan0 (172.20.10.2) และ eth0 (192.168.1.4)
        - เปิดแต่ละ path ด้วย glorytun path addr <IP> set up

     3. ผลการทดสอบ Handshake
        - ทั้ง 2 paths STATUS = running
        - Server เห็น Pi connect มาด้วย Public IP ทั้ง 2 ค่าย
        - Key ตรงกัน (1982E23F...)
        - อย่างไรก็ตาม Ping 10.255.255.1 ยัง fail 100% packet loss
          → ยังไม่ confirm ว่า data flow ผ่าน tunnel จริง

■ ปัญหาที่พบและแนวทางแก้ไข
────────────────────────────────────────────────────────────────────────

  ปัญหา : Glorytun syntax ในเอกสาร MVP (glorytun connect) ใช้ไม่ได้กับ version 0.3.4
  วิเคราะห์: เอกสารเขียนสำหรับ Glorytun version เก่า ซึ่ง syntax แตกต่างกัน
  แก้ไข : อ่าน glorytun help โดยตรง และใช้คำสั่ง bind แทน connect

  ปัญหา : ไฟล์ /etc/iproute2/rt_tables ไม่มีใน Pi OS minimal
  วิเคราะห์: Pi OS minimal ไม่ pre-install ไฟล์นี้มาให้
  แก้ไข : สร้างไฟล์เองพร้อม default content (255 local, 254 main, 253 default, 0 unspec)

  ปัญหา : Server อยู่หลัง CGNAT ของ LTE Router ทำให้ packet จาก Pi ไม่ถึง Server
  วิเคราะห์: ค่ายมือถือใช้ CGNAT — WAN IP ของ Router เป็น private (10.98.247.74)
             แม้ curl ifconfig.me จะแสดง Public IP แต่ Port Forward ไม่ทำงาน
  แก้ไข : ย้าย Server ไปต่อ Fiber ที่มี Public IP จริง (61.91.251.238/29 ที่ enp86s0)

  ปัญหา : ip_forward = 0 บน Pi ทำให้ packet ไม่ไหลผ่าน tunnel แม้ handshake สำเร็จ
  วิเคราะห์: Pi OS ปิด ip_forward ตามค่า default ทำให้ routing ผ่าน tunnel ไม่ทำงาน
  แก้ไข : sysctl -w net.ipv4.ip_forward=1 และบันทึกถาวรใน /etc/sysctl.conf

  ปัญหา : Ping 10.255.255.1 fail 100% packet loss แม้ Glorytun handshake สำเร็จ
  วิเคราะห์: STATUS=running หมายถึง handshake สำเร็จเท่านั้น ไม่ได้ confirm data flow
             ยังไม่ได้ตรวจสอบ tcpdump ทั้ง 2 interfaces บน Server พร้อมกัน
  แก้ไข : [อยู่ระหว่างการ debug — จะดำเนินการต่อในวันถัดไป]

■ งานที่ดำเนินการในวันนี้
────────────────────────────────────────────────────────────────────────

1. พัฒนาระบบ Glorytun Channel Bonding และ Client Router บน Pi 4 (ช่วงเช้า)
   ─────────────────────────────────────────────────────────────────
   พัฒนาและตั้งค่าระบบ Channel Bonding ให้สมบูรณ์ โดยแบ่งเป็น 2 ส่วนหลัก
   ได้แก่ ระบบ Bonding พื้นฐาน และการทำให้ Pi 4 เป็น Router สำหรับ Client

   Phase 1 — Channel Bonding พื้นฐาน:
     - สร้าง glorytun-pi.service (systemd) พร้อม Restart=always
       เพื่อให้ service กลับมาอัตโนมัติเมื่อ tunnel ตาย
     - ตั้ง Policy Routing แยกต่อ interface (eth1 → table 100, eth2 → table 101)
       เพื่อให้แต่ละ WAN path ออก Internet ตรงด้วย interface ของตัวเอง
     - ตั้ง rate fixed tx 100m rx 100m บนทุก path
       (ต้องตั้งทั้ง tx และ rx — ถ้าไม่ตั้ง rx Server จะ TX-RATE = 0 ส่ง reply ไม่ได้)
     - เพิ่ม Watchdog loop ใน wrapper script ตรวจ ping ทุก 10 วินาที
       restart ถ้า fail ติดต่อกัน 3 ครั้ง (แก้ปัญหา tunnel หยุดส่งหลัง 60 นาที)
     - เปลี่ยน source port จาก 5000 → 65000 เพื่อป้องกัน router block

   Phase 2 — Pi 4 เป็น Router สำหรับ Client:
     - ขยาย gt0 subnet จาก /30 → /24 เพื่อรองรับ Client IPs
     - ตั้ง eth0 เป็น LAN gateway (10.255.255.254/24) สำหรับ Client
     - ติดตั้งและตั้งค่า dnsmasq แจก DHCP บน eth0
       (range 10.255.255.10-200, GW .254, DNS 8.8.8.8)
     - ตั้ง nftables FORWARD rule: eth0 ↔ gt0 และ MSS clamping
       สำหรับแก้ปัญหา HTTPS / large packet ผ่าน tunnel
     - ตั้ง gt0 route metric 200 เพื่อให้ eth0 ชนะ client traffic
       ป้องกัน ICMP Redirect จาก Server
     - ตั้ง Server NAT masquerade สำหรับ subnet 10.255.255.0/24

2. ตั้งค่า Dynamic IP / Hot-plug Recovery และทดสอบระบบ (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   เพิ่มความสามารถรองรับ IP เปลี่ยนแบบ dynamic และทดสอบระบบทั้งหมด
   ผ่าน reboot และการถอด/เสียบสายเน็ต

   Phase 3 — Dynamic IP / Auto-recovery:
     - สร้าง NetworkManager wan-auto profile แบบ multi-connect
       (1 profile ใช้ได้กับทุก WAN interface โดยไม่ต้องตั้งค่าเพิ่ม)
     - สร้าง NM Dispatcher /etc/NetworkManager/dispatcher.d/99-glorytun
       update policy routing + glorytun path ทันทีเมื่อ IP เปลี่ยน
     - สร้าง glorytun-sync.timer (OnUnitActiveSec=5s)
       ตรวจและซ่อม path/routing ที่ไม่ sync อัตโนมัติทุก 5 วินาที
     - ตั้ง eth0 เป็น unmanaged ถาวรใน NetworkManager
       ป้องกัน NM ดึง eth0 ไป DHCP ทับ IP ที่ script ตั้งไว้
     - เพิ่ม dnsmasq systemd override After=glorytun-pi.service
       ป้องกัน dnsmasq start ก่อน eth0 มี IP (แก้ "unknown interface eth0")

   Phase 4 — ทดสอบ Reboot และ Failover:
     - ทดสอบ Reboot ครั้งที่ 1: ทุก service ขึ้นอัตโนมัติ
     - ทดสอบ Reboot ครั้งที่ 2 (หลังแก้ dnsmasq + route metric): ผ่าน 10/10 checks
     - ทดสอบ Failover: ถอดสายเน็ต WAN → failover อัตโนมัติ, กลับมา bond ภายใน ~5-10s
     - ผลการทดสอบ Channel Bonding:
         ปกติ 2 เส้น : eth1 ~36-42 Mbps + eth2 ~36-42 Mbps = รวม ~72-83 Mbps
         ถอดสาย eth1 : eth2 ~53-61 Mbps (failover อัตโนมัติ ไม่หลุด connection)
         เสียบสายคืน : กลับมา bond ได้ ~64-84 Mbps อัตโนมัติ

■ สรุปไฟล์ที่สร้าง / แก้ไข
────────────────────────────────────────────────────────────────────────

  Pi 4 (Raspberry Pi OS):
    /etc/systemd/system/glorytun-pi.service             — systemd service หลัก
    /usr/local/bin/glorytun-start.sh                    — wrapper script + watchdog
    /etc/NetworkManager/dispatcher.d/99-glorytun        — update path เมื่อ IP เปลี่ยน
    /usr/local/bin/glorytun-sync.sh                     — sync script (รัน timer ทุก 5s)
    /etc/systemd/system/glorytun-sync.timer             — timer สำหรับ sync script
    /etc/NetworkManager/conf.d/unmanaged-eth0.conf      — ล็อก eth0 ไม่ให้ NM จัดการ
    /etc/NetworkManager/conf.d/wan-auto.nmconnection    — WAN profile แบบ multi-connect
    /etc/systemd/system/dnsmasq.service.d/              — override After=glorytun-pi
    /etc/nftables.conf                                  — FORWARD + MSS clamping rules

■ เทคโนโลยีที่ใช้
────────────────────────────────────────────────────────────────────────

  - Glorytun 0.3.4        — Channel Bonding ผ่าน UDP tunnel (chacha20poly1305)
  - systemd               — Service management + timer สำหรับ sync
  - NetworkManager        — จัดการ WAN interface แบบ dynamic + dispatcher
  - dnsmasq               — DHCP Server บน eth0 สำหรับ Client
  - nftables              — Firewall FORWARD + MSS clamping
  - iproute2              — Policy Routing (ip route, ip rule, routing table)
  - Bash                  — Wrapper script + watchdog loop + sync script

■ ปัญหาที่พบและแนวทางแก้ไข
────────────────────────────────────────────────────────────────────────

  ปัญหา : glorytun process หายหลัง reboot
  วิเคราะห์: ยังไม่มี systemd service ทำให้ process ไม่ถูก start อัตโนมัติ
  แก้ไข : สร้าง glorytun-pi.service พร้อม Restart=always และ WantedBy=multi-user.target

  ปัญหา : mud->window = 0 ทำให้ส่ง data ไม่ได้ และ Server TX-RATE = 0 reply ไม่ได้
  วิเคราะห์: glorytun ใช้ค่า rx ที่ฝั่ง Client ตั้งเป็น server's tx rate
             ถ้าไม่ตั้ง rx rate → Server เห็น rate = 0 → ส่ง reply ไม่ได้
  แก้ไข : ต้องตั้งทั้ง rate fixed tx 100m rx 100m ทุกครั้งที่ add path

  ปัญหา : glorytun หยุดส่ง data หลังผ่านไปประมาณ 60 นาที (kxtimeout)
  วิเคราะห์: kxtimeout ทำให้ session หมดอายุ แต่ process ยังทำงานอยู่
  แก้ไข : เพิ่ม watchdog loop ใน wrapper script ตรวจ ping ทุก 10s
             kill + restart service อัตโนมัติเมื่อ fail ติดต่อกัน 3 ครั้ง

  ปัญหา : Client ping gateway ไม่ได้ — Server ส่ง ICMP Redirect กลับมา
  วิเคราะห์: gt0 และ eth0 อยู่บน subnet 10.255.255.0/24 เหมือนกัน metric เท่ากัน
             kernel เลือก gt0 ส่ง reply ของ Client → Server ส่ง ICMP Redirect กลับ
  แก้ไข : ตั้ง gt0 route metric 200 ให้ eth0 (metric 0) ชนะ client traffic เสมอ
             Server tunnel IP (.1) ยังเข้าถึงได้ผ่าน host route metric 1

  ปัญหา : NetworkManager ดึง eth0 ไป DHCP ทับ IP ที่ script ตั้งไว้
  วิเคราะห์: wan-auto profile แบบ multi-connect จับ eth0 ไปด้วย
  แก้ไข : สร้าง /etc/NetworkManager/conf.d/unmanaged-eth0.conf
             (unmanaged-devices=interface-name:eth0)

  ปัญหา : dnsmasq fail หลัง reboot ด้วย error "unknown interface eth0"
  วิเคราะห์: dnsmasq start ก่อน glorytun-start.sh สร้าง IP บน eth0
  แก้ไข : สร้าง systemd override ให้ dnsmasq มี After=glorytun-pi.service

  ปัญหา : WAN IP เปลี่ยนระหว่าง runtime ทำให้ path degraded
  วิเคราะห์: NM dispatcher trigger ไม่ครบทุก event (เช่น DHCP renew)
  แก้ไข : สร้าง glorytun-sync.timer ทุก 5s ตรวจ IP จริงบน interface
             เทียบกับ rule ที่ register ไว้ — ถ้าไม่ตรงให้ update อัตโนมัติ
