วันจันทร์ที่ 25 พฤษภาคม 2569 (โปรเจกต์: Glorytun Channel Bonding Router)

รายละเอียดงาน: ในช่วงเช้าดำเนินการสร้างชุดเครื่องมือทดสอบ (Test Framework) เพื่อวัดและวิเคราะห์ประสิทธิภาพของอุโมงค์ข้อมูลแบบรวมช่องสัญญาณ (Bonded Tunnel) ก่อนที่จะลองแนวทางแก้ไขปัญหา Bug 23 ใด ๆ เนื่องจากจำเป็นต้องมีข้อมูลเชิงประจักษ์รองรับ โดยสร้างสคริปต์ทั้งสิ้น 4 รายการ ได้แก่ bench-tunnel.sh สำหรับทดสอบ TCP แบบ Matrix ครอบคลุมการรับส่งข้อมูล 1/4/8 Stream ทั้งทิศทาง Upload และ Download จำนวน 3 รอบ รอบละ 30 วินาที, bench-paths.sh สำหรับเก็บค่าแบนด์วิดท์แยกรายช่องทาง WAN ทุก 1 วินาที เพื่อตรวจสอบการกระจายแพ็กเก็ต (Packet Distribution) ของแต่ละเส้นทาง, bench-summary.py สำหรับแปลงผลลัพธ์ JSON ของ iperf3 เป็น Markdown และ probe-ports.sh สำหรับตรวจสอบการเข้าถึงเครือข่ายภายนอก (Outbound Reachability) ของแต่ละ WAN จากนั้นทำการ Deploy ชุดเครื่องมือดังกล่าวบน Mini PC ผ่าน Tailscale และรัน UDP Ceiling Test ที่อัตรา 400 Mbps ซึ่งพบผลลัพธ์สำคัญว่า Glorytun กระจายแพ็กเก็ต 50/50 อย่างสมดุลระหว่างทั้ง 2 เส้นทาง โดยอุโมงค์รองรับการถ่ายทอดข้อมูล UDP ได้ถึง 365–385 Mbps ยืนยันว่าปัญหาไม่ได้อยู่ที่ Tunnel Capacity หรือ CPU ต่อมาทำการทดสอบการปรับ Rate Cap จาก 500m ลดเหลือ 200m พบว่า TX-LOSS ลดลงจาก 1.18% เหลือ 0.39% แต่ Throughput ตกลง 44% ซึ่งถือว่าเป็นผลลัพธ์ที่ไม่คุ้มค่า รวมถึงทดสอบ MTU Sweep โดยตรวจสอบ Path MTU จริงและพบว่า PC→Server ถูกจำกัดที่ 1492 Bytes ส่งผลให้ค่า MTU เดิม 1442 ทำให้ Outer Packet ชน Path MTU โดยไม่มี Safety Margin จึงปรับเป็น MTU 1438 และค้นพบว่า Glorytun-mud มี MTU 2 ชั้น คือ Link MTU ที่สามารถตั้งค่าได้ผ่าน ip link set และ Internal MTU ที่ Glorytun กำหนดเองที่ 1442 เสมอโดยไม่อนุญาตให้ Override นอกจากนี้ยังทำการทดสอบผ่าน fast.com API โดยตรงจาก Server เพื่อตรวจสอบสมมติฐานว่าผลการทดสอบความเร็วที่ต่ำเกิดจากปัญหา Netflix Open Connect Peering โดยพบว่า Netflix OCA ในกรุงเทพฯ ให้ความเร็ว 517–533 Mbps โดยตรง ในขณะที่ OCA ในยุโรปอย่าง Budapest, Sofia และ Warsaw ให้เพียง 4.6–6.6 Mbps และ fast.com ทำการวัดผลโดยเฉลี่ยจาก Server ทั้ง 5 ตัวพร้อมกันซึ่งรวม EU Server 3 ตัวด้วย ทำให้ผลถูกฉุดลงโดยไม่ใช่ข้อบกพร่องของระบบ ในช่วงบ่ายทำการ Migrate ระบบกลับมายัง Raspberry Pi 4 ซึ่งออฟไลน์มา 2 วัน โดยตรวจพบว่า Pi มีค่า Config ที่ไม่ตรงกับมาตรฐานปัจจุบัน ได้แก่ MTU ยังเป็น 1350 และ Beat ยังเป็น 30ms จึงดำเนินการปรับแก้ทั้งหมด รวมถึงแก้ไข Tailscale ที่ขึ้นสถานะ Logged Out และตั้งเวลาของ Pi ด้วยตนเองจากนั้นทำการ Hardware Cutover โดย Stop Mini PC, ย้าย USB ASIX Adapter และสาย LAN ไปยัง Pi และทดสอบเปรียบเทียบประสิทธิภาพ พบว่า Pi ด้วย Rate Cap 200m ชนะ Mini PC ด้วย Rate Cap 500m ในทุกกรณี โดยเฉพาะ Download Single Stream ที่ Pi ให้ผลสูงกว่าถึง 665% (41.3 Mbps vs 5.4 Mbps) เนื่องจากอัตราการสูญเสียข้อมูล (Packet Loss Rate) ของ Pi อยู่ที่ 0% ขณะที่ Mini PC มี RX-LOSS 0.78% ซึ่งสอดคล้องกับสูตร Mathis ที่ระบุว่า Throughput ของ TCP แปรผกผันกับค่ารากที่สองของ Loss ในช่วงเย็นดำเนินการยืนยัน Bug 23 ด้วย Controlled Test โดยปิด Path ทีละเส้นผ่าน Software พบว่า ISP B เส้นเดียวให้ประสิทธิภาพสูงกว่าการใช้ Bonding ถึง 3 เท่า และค่า Retransmission ต่ำกว่าถึง 10 เท่า จากนั้นทดลองแนวทางแก้ไข 2 แบบ ได้แก่ Asymmetric Rate Weighting และ losslimit 5% แต่ทั้งสองแนวทางไม่สามารถแก้ปัญหาได้ สรุปว่าปัญหา Bug 23 เป็นข้อจำกัดเชิงสถาปัตยกรรมของ Glorytun ที่จำเป็นต้องเปลี่ยนไปใช้ OpenMPTCPRouter ซึ่งทำ Per-flow MPTCP Bonding แทนการกระจายแพ็กเก็ตระดับ Packet

ปัญหาและแนวทางการแก้ไข:

ปัญหาสัญญาณรบกวนบนเครือข่ายภายในบ้าน (LAN Noise Variance) ทำให้ผลการทดสอบมีความคลาดเคลื่อนสูง: ตรวจพบว่าความแปรปรวนของผลการวัดอยู่ที่ ±20–30% ต่อชั่วโมง เนื่องจากมีอุปกรณ์ Client ใช้งานอุโมงค์พร้อมกัน 7–8 เครื่อง ส่งผลให้การทดสอบ MTU ที่แตกต่างกันเพียง 1 Byte ไม่สามารถอ่านผลได้อย่างแม่นยำแม้ทดสอบห่างกันเพียง 25 นาที
แนวทางแก้ไข: กำหนดให้ดำเนินการทดสอบ A/B แบบ Back-to-back ทันทีติดต่อกัน และหากต้องการผลที่แม่นยำสูงควรดำเนินการในช่วงดึกที่ไม่มีการใช้งานภายในบ้าน

ปัญหา MTU ของ Glorytun มี 2 ชั้นที่ทำงานแยกกัน (Glorytun Internal MTU): ตรวจพบว่า Glorytun-mud ทำการตรวจสอบ Internal MTU อัตโนมัติและกำหนดค่าไว้ที่ 1442 เสมอโดยไม่อนุญาตให้ Override ซึ่งแตกต่างจาก Link MTU ที่ตั้งค่าได้ผ่านคำสั่ง ip link set และทุกครั้งที่ Restart Service Glorytun จะ Override ค่า MTU ที่ตั้งไว้กลับเป็น 1442 ทันที
แนวทางแก้ไข: ยอมรับว่า Internal MTU = 1442 เปลี่ยนไม่ได้ และดำเนินการหยุด Sync Timer ก่อนแล้วจึงตั้ง Link MTU 1438 หลัง Glorytun Start เพื่อให้ TCP MSS Clamping ผ่าน nftables ทำงานได้อย่างมีประสิทธิภาพ ส่งผล MSS = 1398 ช่วยลด Queue Pressure ได้บ้าง

ปัญหาข้อจำกัดของ Glorytun (Bug 23) จากการสลับลำดับแพ็กเก็ต (Packet Reordering Penalty): ตรวจพบว่าความเร็ว TCP Single Stream ผ่าน Bonded Tunnel ถูกจำกัดที่ประมาณ 120 Mbps ทั้งที่ทรัพยากรระบบยังมีเหลือ โดย ISP B เส้นเดียวให้ประสิทธิภาพสูงกว่าการใช้ Bonding ถึง 3 เท่า และค่า Retransmission ต่ำกว่าถึง 10 เท่า
แนวทางแก้ไข: ทดลอง Asymmetric Rate Weighting (ISP B 300m, ISP A 100m) พบว่า RX-LOSS พุ่งสูงถึง 4.31% เพราะ Glorytun ไม่ได้ Split Proportional ตาม Rate แต่ Push ตาม Target Rate ทำให้ ISP B รับไม่ไหว และทดลอง losslimit 5% พบว่าไม่ Kick เพราะ Glorytun ใช้ Running Average ช่วง 10 วินาที สรุปว่าจำเป็นต้องเปลี่ยนสถาปัตยกรรมไปใช้ OpenMPTCPRouter ในโอกาสต่อไป

วันอังคารที่ 26 พฤษภาคม 2569 (โปรเจกต์: Glorytun Channel Bonding Router & Face Attendance System)

รายละเอียดงาน: ในช่วงเช้าดำเนินการติดตั้ง OpenMPTCPRouter (OMR) บน Mini PC อีกเครื่องหนึ่งในฐานะ Test Bed แยกออกจากระบบ Production ของ Raspberry Pi 4 เพื่อให้สามารถเปรียบเทียบทั้ง 2 แนวทางในสภาพแวดล้อมจริงโดยไม่กระทบการทำงานของระบบหลัก ต่อมาในช่วงบ่ายพบว่า Tailscale ของ Pi ไม่สามารถเชื่อมต่อได้ จึงเข้าผ่าน LAN โดยตรงที่ IP 192.168.1.2 และตรวจพบว่านาฬิกาของ Pi ช้ากว่า Server ถึง 3 ชั่วโมง 7 นาที อันเป็นสาเหตุที่ทำให้ Glorytun-mud ทิ้งแพ็กเก็ตทั้งหมดเงียบ ๆ เนื่องจาก Timestamp อยู่นอกช่วง Replay Window จึงดำเนินการตั้งเวลาด้วยตนเองทันที หลังจากนั้น Tunnel กลับมาทำงานภายใน 10 วินาที และ Restart Tailscale ให้กลับมาออนไลน์ได้ที่ IP 100.82.150.4 เพื่อป้องกันปัญหาเดิมจากเกิดซ้ำ จึงวางระบบป้องกันถาวร 2 ชั้น โดยชั้นแรกสร้าง htpdate-boot.service เป็น One-shot Service ที่รัน Before=glorytun-pi.service ดึงเวลาจาก HTTPS Date Header ของ google.com, cloudflare.com และ apple.com ผ่าน Port 443 ซึ่ง ISP ไม่เคยบล็อก ให้ความแม่นยำประมาณ 1 วินาที ซึ่งอยู่ในช่วง Replay Window ของ Glorytun และชั้นที่สองติดตั้ง chrony บน Server โดยเพิ่ม allow 100.64.0.0/10 ใน chrony.conf เพื่อให้บริการ NTP แก่ Subnet ของ Tailscale จากนั้นติดตั้ง chrony บน Pi โดยกำหนด server 100.65.195.27 iburst เพื่อ Sync แบบต่อเนื่องขณะระบบทำงานผ่าน Tailscale IP ซึ่งไม่ถูก ISP บล็อก พร้อมทั้งเพิ่ม Drop-in /etc/systemd/system/glorytun-server.service.d/wait-for-time.conf บน Server ให้มี After=chrony.service time-sync.target เพื่อป้องกัน Race Condition ตอน Server Reboot ในช่วงเย็นใช้โอกาสที่ Client โหลดเกมบน Client เก็บ Bandwidth Log เป็นเวลา 15 นาที ทุก 2 วินาที รวม 441 ตัวอย่าง พบค่า Download p50 อยู่ที่ 82 Mbps, p95 อยู่ที่ 107 Mbps และสูงสุดที่ 118 Mbps โดย eth1 รับได้สูงสุด 137 Mbps ซึ่งใกล้เคียง ISP A Line Speed และค่า Encapsulation Overhead อยู่ที่ 22% พร้อมทั้งตรวจพบเหตุการณ์ที่ ISP A สะดุดนาน 26 วินาที ตั้งแต่เวลา 20:47:44–20:48:10 โดย TX-LOSS สะสมสูงถึง 44.7% แล้วกู้คืนเองได้โดยอัตโนมัติโดยไม่ต้อง Restart ซึ่งเป็นหลักฐานยืนยันการทำงานของระบบ Self-healing อีกทั้งได้จัดทำชุดเอกสารหลักฐาน (Evidence Pack) จำนวน 10 ไฟล์ ประกอบด้วย SUMMARY.txt, สถานะ Service, ข้อมูล Time Sync, Tunnel State, Watchdog History 24 ชั่วโมง, Boot Ordering, Backup Inventory, Bandwidth Log 441 ตัวอย่าง และผลเปรียบเทียบ PC vs Pi และ Bonded vs Single ตลอดจนซ้อมนำเสนอรายงานสรุปผลการฝึกงานครอบคลุม 2 โปรเจกต์หลักตลอด 11 สัปดาห์ ร่วมกับสมาชิกในกลุ่มอีก 2 คน โดยใช้ Presentation ปัญหาและแนวทางการแก้ไข:

ปัญหา Bug 27 นาฬิกาของ Pi คลาดเคลื่อนจาก Server ถึง 3 ชั่วโมง 7 นาที ทำให้ Tunnel Handshake ล้มเหลวเงียบๆ (Clock Skew): ตรวจพบว่า Pi ไม่มีแบตเตอรี่ RTC ประกอบกับ NTP UDP Port 123 ถูก ISP บล็อก ทำให้ไม่ได้ Sync เวลาตั้งแต่ครั้งก่อนที่ Tailscale หยุดทำงาน ส่งผลให้ Glorytun ทำการทิ้งแพ็กเก็ตที่มี Timestamp นอกช่วง Replay Window โดยไม่แสดงข้อผิดพลาดใดๆ
แนวทางแก้ไข: ตั้งเวลาด้วยตนเองทันทีโดยอ้างอิงจาก Server แล้ว Restart glorytun-pi.service จากนั้นวางระบบป้องกันถาวร 2 ชั้น คือ htpdate HTTPS Boot-time Sync ผ่าน Port 443 และ chrony Runtime Sync ผ่าน Tailscale IP ซึ่งไม่ถูก ISP บล็อก

ปัญหา htpdate บน Server คำนวณ Offset ผิดพลาดอย่างรุนแรง (HTTPS Time Sync Offset Error): ตรวจพบว่าเมื่อ apple.com Timeout เพียง 1 ใน 3 Host htpdate คำนวณ Offset ผิดพลาดและพยายามตั้งเวลาเป็นปี ค.ศ. 1970 อาจทำให้ Service อื่น ๆ ที่ขึ้นกับเวลาระบบเสียหาย
แนวทางแก้ไข: นำ htpdate ออกจาก Server เนื่องจาก Server เป็น x86 มี CMOS Battery และ NTP ไม่ถูก ISP บล็อกอยู่แล้ว การใช้ chrony อย่างเดียวเพียงพอและยังช่วยลดพื้นที่เสี่ยงของระบบ (Attack Surface) อีกด้วย

รายละเอียดงาน: ในช่วงเช้าดำเนินการเข้าประชุมศูนย์ตามตาราง เพื่อรายงานความคืบหน้าของทั้ง 2 โปรเจกต์ โดยรายงานสถานะปัจจุบันของ Face Attendance System และแจ้งทิศทางการแก้ไขปัญหา Bug 23 ด้วยการ Migrate ไปใช้ OpenMPTCPRouter รวมถึงรายงานผลการทดสอบ Mini PC (OMR) ในฐานะ Test Bed ขนานกับ Pi 4 ที่ดำเนินการไปแล้ว และรายงาน Bug 27 เรื่อง Clock Skew ที่แก้ไขเรียบร้อยแล้วด้วยระบบ 2 ชั้น จากนั้นในช่วงบ่ายเริ่มกระบวนการ Migrate Raspberry Pi 4 จาก Glorytun ไปยัง OMR ตามลำดับขั้นตอน โดยเริ่มจากการเปิดการเชื่อมต่อ SSH บน OMR Server ซึ่งติดตั้งบน Debian 13 (Trixie) เครื่องเดียวกับ VPN Server เดิม ด้วยการติดตั้ง openssh-server และกำหนด Port 65022 เพื่อหลีกเลี่ยง Bot Scan พร้อมทั้งติดตั้ง RustDesk Client v1.4.6 บน Laptop Ubuntu 24.04 เพื่อใช้ Remote Desktop เข้า Server จากนั้นดำเนินการแก้ไข Firewall บน OMR Server ที่ติดตั้ง nftables Policy DROP ทั้ง INPUT และ OUTPUT โดยไม่มี tailscale0 อยู่ใน Allowlist ทำให้ SSH ผ่าน Tailscale ไม่ผ่าน ต่อมาสำรวจ OMR Server พบว่ารัน omr-vps-admin version 0.16 โดยมี VPN Backend หลายตัวทำงานขนานกัน ทั้ง shadowsocks-rust, glorytun UDP 65001, mlvpn, openvpn และ xray ก่อน Flash SD Card จะทำการสำรองข้อมูล Config ของ Pi 4 ที่สำคัญทั้งหมดรวม 39 ไฟล์ ขนาด 126 KB ผ่านการเชื่อมต่อสาย LAN โดยตรงจาก Laptop ไปยัง Pi จากนั้น Download OMR Pi 4 Factory Image เวอร์ชัน v0.63-6.12-r0 ขนาด 68.5 MB และทำการยืนยัน Device Path 2 รอบก่อน Flash เพื่อป้องกันการเขียนผิด Device โดยใช้ dd ผ่าน zcat ส่งผลให้ Pi Boot ด้วย OMR สำเร็จที่ OpenMPTCProuter v0.63-6.12 บน Kernel 6.12.40 aarch64 และสามารถ SSH เข้า Pi ได้ที่ IP 192.168.100.1 อย่างไรก็ตามพบว่า WAN Interface ไม่ได้รับ IP Address จาก DHCP ของ Router เนื่องจาก OMR Factory Image กำหนด WAN เป็น MACVLAN Mode VEPA ซึ่งไม่เข้ากันกับ Consumer Router จึงดำเนินการแก้ไขผ่าน uci จนสำเร็จ แต่หยุดกระบวนการ Pairing ไว้เพื่อดำเนินการ Cutover เต็มรูปแบบในวันถัดไป

ปัญหาและแนวทางการแก้ไข:

ปัญหา Bug 28 การเชื่อมต่อ SSH ผ่าน Tailscale ไปยัง OMR Server หมดเวลา (SSH Tailscale Timeout): ตรวจพบจาก tcpdump ว่า SYN Packet ถึง tailscale0 แต่ไม่มี SYN-ACK ตอบกลับ เนื่องจาก OMR ติดตั้ง nftables Filter Table พร้อม INPUT และ OUTPUT Policy DROP โดยมี Allowlist เฉพาะ Interface เดิม ทำให้ tailscale0 ถูก Drop ทุก Packet
แนวทางแก้ไข: เพิ่มกฎ iptables -I INPUT/OUTPUT 1 สำหรับ tailscale0 ทันที และสร้าง Hook Script /etc/network/if-up.d/99-tailscale-accept เพื่อให้กฎนี้ถูก Apply อัตโนมัติทุกครั้งที่ Interface tailscale0 ขึ้นมาทำงาน

ปัญหา Bug 29 WAN Interface ของ OMR Pi ไม่ได้รับ IP Address จาก DHCP ของ Router (MACVLAN VEPA Incompatibility): ตรวจพบว่า OMR Factory Image ตั้งค่า WAN เป็น MACVLAN Mode VEPA ซึ่งต้องการ Switch ที่รองรับการสะท้อน Frame (VEPA Frame Reflection) แต่ Router ภายในบ้านไม่รองรับ ทำให้ DHCP Request หมดเวลาเงียบๆ แม้สาย Ethernet, Router และ Link จะทำงานปกติ ยืนยันโดยการรัน udhcpc -i eth1 ตรงๆ ซึ่งได้รับ IP 192.168.1.3 ทันที
แนวทางแก้ไข: ใช้คำสั่ง uci เพื่อ Bypass MACVLAN โดยลบ .type และ .masterintf ออก แล้วตั้ง wan1 ให้ใช้ Physical Interface eth1 โดยตรงพร้อม DHCP Protocol ส่งผลให้ wan1 ได้รับ IP 192.168.1.3 และสามารถ ping 1.1.1.1 ได้ทันที

ปัญหา Heredoc ผ่าน RustDesk ทำให้ Shell รอ EOF ไม่สิ้นสุด (RustDesk Paste Indentation): ตรวจพบว่า RustDesk เพิ่ม Leading Whitespace ก่อน EOF Token ทำให้ Shell ไม่รู้จัก Closing Delimiter และรอรับ Input อย่างไม่มีที่สิ้นสุด
แนวทางแก้ไข: เปลี่ยนมาใช้ printf '...' | sudo tee แทน Heredoc ทั้งหมดเพื่อหลีกเลี่ยงปัญหา Indentation ที่เกิดจากการ Paste ผ่าน Remote Desktop

วันพฤหัสบดีที่ 28 พฤษภาคม 2569 (โปรเจกต์: Glorytun/OMR Channel Bonding Router)

รายละเอียดงาน: ในช่วงเช้าดำเนินการ Pairing ระหว่าง Raspberry Pi 4 กับ OMR Server ผ่าน Web UI ที่ https://192.168.120.1 โดยกรอกข้อมูล VPS IP, User Admin, Password และ Port 65500 แต่หลังจาก Save พบ Error ครบชุดจาก Network Overview ทั้ง ShadowSocks Rust ไม่รัน, VPN ไม่รัน และไม่สามารถดึง Token ได้ จึงตรวจสอบผ่าน uci show และพบว่า IP Address ที่บันทึกไว้มี Space นำหน้า (' 125.25.38.138') ทำให้ Script Parse Path พัง และ shadowsocks-rust เกิด Crash Loop 6 ครั้ง หลังจากแก้ไขผ่าน uci โดยตรงแล้ว Log ฝั่ง Server เริ่มเห็น Pi ทั้ง 2 WAN ทำ GET /status และ /clienthost ทุก 5 วินาที ยืนยัน Pairing สำเร็จในระดับ Admin API อย่างไรก็ตามพบว่ายังมีปัญหา Proxy Mismatch เนื่องจาก Pi ใช้ shadowsocks-rust เป็นค่าเริ่มต้น แต่ Server รัน shadowsocks-go ทำให้ Key ไม่ตรงกัน จึงเลื่อนการแก้ไขส่วนนี้ไปดำเนินการในวันถัดไป ในช่วงบ่ายดำเนินการเขียน Reverse SSH Tunnel Service ใหม่ทั้งหมดเป็น procd-based แทน Init Script เดิมที่มีปัญหาสำคัญ 3 ประการ ได้แก่ ไม่มี Respawn เมื่อ SSH ขาด, stop() ใช้ killall ssh ซึ่งกระทบทุก SSH Session บนระบบ และมี Duplicate Process ค้างอยู่ 2 ตัว โดย Service ใหม่ใช้ procd_set_param respawn 10 5 0 พร้อม ExitOnForwardFailure=yes และ ServerAliveInterval=15 ทำให้ procd จัดการ Kill เฉพาะ Instance ของ Service และ Respawn ภายใน 5 วินาที ทดสอบด้วย kill -9 แล้วยืนยันว่า Respawn ทำงานสำเร็จและสร้าง rc.d Symlinks สำหรับ Auto-start on Boot จากนั้นพบปัญหา Zombie sshd-session บน Server ที่ยึด Port 9090 ค้างนานกว่า 10 นาทีหลัง Pi Reboot ตรวจสอบด้วย lsof พบ sshd-session PID 2960097 อยู่ใน LISTEN และ CLOSE_WAIT 16 การเชื่อมต่อ จึง Kill PID ดังกล่าวและแนะนำเพิ่ม ClientAliveInterval=30 บน Server เพื่อป้องกันการเกิดซ้ำ สุดท้ายดำเนินการจัดทำ Pi OMR Backup แบบเต็มรูปแบบโดยเพิ่ม Custom Path ใน /etc/sysupgrade.conf แล้วรัน sysupgrade -b ได้ Backup ขนาด 89 KB ครอบคลุม 281 รายการ ประกอบด้วย UCI Config ทั้งหมด, SSH Host Identity, Credentials, RC Scripts, SSH Keys และ Custom Scripts ซึ่ง Restore แล้วใช้งานได้ทันทีโดยไม่ต้องตั้งค่าเพิ่ม

ปัญหาและแนวทางการแก้ไข:

ปัญหา Typo Space นำหน้า IP Address ใน Form ทำให้ shadowsocks-rust เกิด Crash Loop (VPS IP Whitespace Bug): ตรวจพบจาก uci show ว่า openmptcprouter.vps.ip=' 125.25.38.138' มี Space นำหน้า ทำให้ Script Parse Path พัง และ shadowsocks-rust Crash ซ้ำแล้วซ้ำเล่า 6 ครั้ง แม้ Network สามารถเชื่อมต่อได้ปกติ
แนวทางแก้ไข: แก้ไขตรงๆ ผ่าน uci set openmptcprouter.vps.ip='125.25.38.138' แล้ว uci commit และ Restart Service ส่งผลให้ Pairing สำเร็จในระดับ Admin API ทันที

ปัญหา Zombie sshd-session บน Server ยึด Port 9090 ค้างนานกว่า 10 นาทีหลัง Pi Reboot (Zombie SSH Session): ตรวจพบจาก lsof ว่า sshd-session PID 2960097 ยังคง LISTEN บน Port 9090 พร้อม CLOSE_WAIT อีก 16 การเชื่อมต่อ เนื่องจาก Server ไม่มี ClientAliveInterval จึงไม่ทราบว่า Client หายไปแล้ว
แนวทางแก้ไข: Kill PID ดังกล่าวทันที ส่งผลให้ Pi Respawn ภายใน 10 วินาทีและ Bind Port 9090 สำเร็จ พร้อมแนะนำเพิ่ม ClientAliveInterval=30 และ ClientAliveCountMax=3 ใน /etc/ssh/sshd_config.d/timeout.conf บน Server เพื่อป้องกันการเกิดซ้ำในระยะยาว

ปัญหา scp ไปยัง OpenWRT Pi ล้มเหลวเพราะ Dropbear ไม่มี SFTP Server (SCP SFTP Protocol Incompatibility): ตรวจพบว่า scp เวอร์ชันใหม่ใช้ SFTP Protocol เป็นค่าเริ่มต้น แต่ Dropbear บน OpenWRT ไม่รองรับ ทำให้การถ่ายโอนไฟล์ล้มเหลว
แนวทางแก้ไข: ใช้ Flag scp -O เพื่อบังคับให้ใช้ Legacy SCP Protocol แทน ส่งผลให้สามารถ Copy Pi OMR Backup ขนาด 89 KB จำนวน 281 รายการกลับมายัง Laptop ได้สำเร็จ

วันศุกร์ที่ 29 พฤษภาคม 2569 (โปรเจกต์: Face Attendance System)

รายละเอียดงาน: ในช่วงเช้าดำเนินการ Merge Branch maevVersion เข้าสู่ Main Branch แบบ Merge Commit (--no-ff) รวมงานพัฒนาทั้งหมดตั้งแต่ Version 14 ถึง 17 ครอบคลุม 111 ไฟล์และประมาณ 16,000 บรรทัด ประกอบด้วย JWT Authentication, Offline Queue, User Management และ Watchdog Monotonic Fix จากนั้นดำเนินการวิเคราะห์ requirements.txt เพื่อเตรียมลงระบบบน NVIDIA Jetson Orin Nano พบว่าไฟล์เดิมเป็น pip freeze จากเครื่อง x86_64 ซึ่งมี torch+cu126 และ nvidia-*-cu12 ที่ไม่มี aarch64 Binary บน PyPI โดยวิเคราะห์แล้วพบว่าโค้ดจริงต้องการเพียง cv2, insightface, onnxruntime, mediapipe, FastAPI stack, psycopg และ auth libs เท่านั้น ส่วน torch/tensorflow ติดมาเพราะด่าน MiniFASNet ด่านเดียว จึงสร้าง requirements-jetson.txt แยกพร้อมคู่มือติดตั้ง จากนั้น SSH เข้า Jetson ที่ตั้ง SSH Key ไว้แล้ว onnxruntime-gpu 1.23.0 และ mediapipe 0.10.14 พร้อมแก้ปัญหา Dependency Conflict ระหว่าง numpy และ opencv ตั้งค่า FAS_ENABLED=False เพื่อตัดการพึ่งพา torch ออก ติดตั้ง PostgreSQL Local พร้อม FPS, ทุก Endpoint ตอบ 200 และ START Button Spawn main+api สำเร็จ เข้าเว็บที่ http://192.168.1.101 ได้ ในช่วงบ่ายพัฒนาฟีเจอร์ 3 โหมดการทำงานต่อกล้อง ได้แก่ โหมด faceatten ซึ่งเป็นระบบเดิมครบชุด, โหมด detect สำหรับตรวจจับและระบุตัวตนโดยแสดงข้อมูลคนแต่ไม่บันทึกลงเวลา และโหมด cctv สำหรับดูภาพสดอย่างเดียวโดยข้ามการโหลด InsightFace เพื่อประหยัด GPU โดยแก้ไข config.py เพิ่ม CAMERA_MODES, main.py ให้ ปัญหาและแนวทางการแก้ไข:

ปัญหา requirements.txt เดิมใช้บน Jetson (aarch64) ไม่ได้ (Platform-Specific Dependency): ตรวจพบว่าไฟล์เดิมเป็น pip freeze จากเครื่อง x86_64 ประกอบด้วย torch+cu126 และ nvidia-*-cu12 ซึ่งไม่มี aarch64 Binary บน PyPI ทำให้ติดตั้งไม่ได้ และ torch ติดมาเพราะ MiniFASNet ด่านเดียวในระบบ Anti-Spoofing
แนวทางแก้ไข: สร้าง requirements-jetson.txt แยก ใช้ Index jetson-ai-lab.io/jp6/cu126 สำหรับ onnxruntime-gpu และ mediapipe พร้อมตั้ง FAS_ENABLED=False ตัดการพึ่งพา torch ออกทั้งหมด ลดจำนวน Dependency ลงอย่างมีนัยสำคัญ

ปัญหา InsightFace 4 Instance รันพร้อมกันทำให้ GPU หน่วยความจำเต็ม (GPU OOM on Orin Nano): ตรวจพบ Error CUBLAS_STATUS_ALLOC_FAILED เมื่อพยายามโหลด InsightFace 4 Instance พร้อมกันบน Jetson Orin Nano ที่มี RAM 7.4 GB เนื่องจาก buffalo_l Model ใช้ VRAM สูง
แนวทางแก้ไข: ลด cameras.json เหลือเพียง IP Camera 1 ตัว ทำให้มีเพียง 1 InsightFace Instance ระบบสามารถทำงานได้ที่ 19 FPS บน GPU อย่างเสถียร

ปัญหาการสลับโหมดกล้องขณะรันทำให้กล้องดับ (Race Condition on Mode Switch): ตรวจพบว่า cam_start Watcher ทำการ Spawn Worker ใหม่ทันทีโดยไม่รอ Worker เก่าสิ้นสุดการทำงาน ส่งผลให้ 2 Worker เปิด VideoCapture อุปกรณ์เดียวกันพร้อมกัน และ Graceful Exit ออกจากกระบวนการกลางคันเมื่อเหลือกล้องเพียงตัวเดียว
แนวทางแก้ไข: แก้ไข main.py ให้ cam_start Watcher ทำการ join() Worker เก่าก่อน Spawn Worker ใหม่ พร้อมเพิ่ม Guard ป้องกัน Graceful Exit เมื่อมี cam_start Flag ค้างอยู่ และปรับ Frontend ให้เรียก Restart แบบ Atomic เพียงครั้งเดียว

ปัญหา IP Camera เปลี่ยนเป็นโหมด cctv ทำให้กล้องทั้งหมดในระบบดับ (FFmpeg Thread-Safety Violation): ตรวจพบ Error "Assertion fctx->async_lock failed at libavcodec/pthread_frame.c:175" ซึ่งเกิดจาก ThreadedCamera.release() เรียก cap.release() ขณะที่ Reader Thread ยังอยู่ใน cap.read() ทำให้ 2 Thread แตะ FFmpeg Context เดียวกันพร้อมกันจนเกิด abort() ทั้ง Process โดยปัญหานี้เกิดเฉพาะ IP Camera ที่ใช้ H.264 Decoder ของ FFmpeg ซึ่งมี Frame-Threading แต่ USB Camera ใช้ V4L2 จึงไม่เจอ
แนวทางแก้ไข: แก้ไข camera.py ให้ release() ทำการ join() Reader Thread ก่อนเรียก cap.release() เสมอ ยืนยันผลโดยนับ Assertion Count = 0 หลังสลับโหมดซ้ำบนเครื่อง dev จริง
