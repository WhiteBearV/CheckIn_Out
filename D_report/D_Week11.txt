1. สร้าง Test Framework + ค้นหาสาเหตุ Bug 23 ระดับลึก (ช่วงเช้า)
   ─────────────────────────────────────────────────────────────────
   Bug 23 ที่ค้างมาจาก session 22 พ.ค. — TCP single-stream ผ่าน bonded
   tunnel ตันที่ ~120 Mbps ทั้งที่ทุก resource ของ Mini PC ยังว่าง
   (CPU/NIC/rate cap headroom 50–87%) ก่อนจะลอง workaround ใด
   ต้องวัดได้ก่อน จึงสร้าง bench harness เก็บไว้ที่
   /home/maeb/glorytun-debug/bench/ ก่อนเลย:

     - bench-tunnel.sh  — TCP matrix (1/4/8 streams × up/down × 3 runs × 30s)
     - bench-paths.sh   — single iperf3 run พร้อม sample byte counter wan1/wan2
                          ทุก 1 วินาที (เพื่อดู per-WAN distribution)
     - bench-summary.py — parser JSON ของ iperf3 → markdown
     - probe-ports.sh   — ตรวจ outbound reachability ของแต่ละ WAN

   deploy ไปบน Mini PC (ผ่าน Tailscale) แล้วรัน baseline TCP matrix
   + UDP ceiling test ที่ rate 400 Mbps ทั้ง upload/download ทันที

   ผลลัพธ์ UDP test ได้ insight สำคัญ:
     - glorytun split packet 50/50 perfectly ทั้ง 2 paths ทั้ง 2 ทิศทาง
       (wan1 tx 202.1 vs wan2 tx 202.5 / wan1 rx 198.0 vs wan2 rx 198.2)
     - tunnel UDP carry ได้ ~365–385 Mbps decrypted → ไม่ได้ตันที่ tunnel/CPU
     - ตัด hypothesis "packet ไปขาเดียว" + "tunnel capacity" ออกได้

   ทดลอง rate sweep — ลด rate cap 500m → 200m:
     - TX-LOSS ลดจาก 1.18% → 0.39% (ดีขึ้นจริง) แต่ throughput ตก 44%
       (net negative) → ตัด hypothesis rate cap อีกตัว

   ทดลอง MTU sweep:
     - ตรวจ path PMTU จริงพบว่า PC→server = 1492 (server-side ISP hop
       จำกัด) ส่วน PC→8.8.8.8 ได้ 1500 (server-side bottleneck คุมไม่ได้)
     - ตอนนั้น gt0 MTU = 1442 → outer packet 1492 = ชน path MTU เป๊ะ
       ไม่มี safety margin
     - A/B test MTU 1442 vs 1280: 3/4 case ช้าลง → revert
     - A/B test MTU 1438 (vs 1442): retx ดีขึ้นเล็กน้อย → apply 1438 ใน
       script ของทั้ง Pi และ Mini PC + server ให้ persist
     - ค้นพบสำคัญ: glorytun-mud มี MTU 2 ค่า — link MTU (kernel) ตั้งได้
       ผ่าน ip link set แต่ glorytun-internal MTU เป็น 1442 เสมอ
       (auto-probe, override ไม่ได้) อย่างไรก็ตาม link MTU 1438 ยังมีผล
       ต่อ TCP MSS clamping ใน nftables (rt mtu) → MSS = 1398 ช่วยลด
       queue pressure ได้บ้าง

   ตรวจสอบสมมติฐาน "fast.com ช้า = peering server-Netflix แย่":
     - ใช้ fast.com API จาก server ตรงๆ ไม่ผ่าน tunnel
     - Netflix Open Connect ใน TOT-BKK (อยู่ใน datacenter เดียวกับ server!):
       517–533 Mbps direct
     - Netflix OCA ในยุโรป (Budapest/Sofia/Warsaw): 4.6–6.6 Mbps direct
     - fast.com test ที่เห็น 5–10 Mbps ผ่าน tunnel ไม่ใช่ peering issue
       แต่เป็น methodology — fast.com ขอ 5 server, ได้ Thai 2 ตัว + EU 3 ตัว
       parallel แล้วเฉลี่ย → ผลถูก European OCAs ฉุดลง
     - Netflix streaming จริงไม่กระทบ (Netflix เลือก Thai OCA เท่านั้น)

2. Migration กลับ Pi 4 + เทียบสมรรถนะ (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   Apply MTU 1438 ถาวร — แก้ glorytun-start.sh + glorytun-server.service
   ทั้ง 2 ฝั่ง + backup ไฟล์เดิมก่อน ปรากฏว่าเมื่อ service restart,
   glorytun reset link MTU กลับเป็น 1442 ทันที (ตั้ง MTU เองจาก probe)
   พบว่าต้อง stop sync timer ก่อนถึงจะตั้ง 1438 stable ได้

   ตรวจดู Pi เก่า (offline 2 วันบน Tailscale) — Pi ปิดอยู่ เปิด Pi
   โดยจ่ายไฟผ่าน USB จาก laptop (USB-C ของ Pi 4 = power only ไม่ใช่
   network gadget mode)

   หา Pi บน network ไม่เจอในตอนแรก — scan 192.168.1.0/24 +
   10.255.255.0/24 + Tailscale หมด ไม่เจอ Raspberry Pi MAC
   (b8:27:eb/dc:a6:32/e4:5f:01) จนกระทั่ง SSH ผ่านทันทีที่ 192.168.1.6
   พบว่า DTC (Debian 13 trixie, ARM64) — user ถอด USB ASIX (wan2 ของ PC)
   ไปเสียบ Pi ตอนแรก Pi ได้ DHCP IP เดิมของ adapter นั้น (.6) เพราะ
   MAC เดียวกัน

   Audit Pi 6 จุดเทียบกับ PC พบว่า config ส่วนใหญ่ถูกแล้ว ยกเว้น:
     - script MTU 1350 (ของเก่า ไม่ใช่ 1438 ที่เป็น new standard)
     - dispatcher + sync.sh ใช้ beat 30ms (ของเก่า ไม่ใช่ 50ms)
     - Tailscale: NoState, logged out, DNS resolve fail (Bug 15 อาการกลับมา)
     - Pi clock เพี้ยน 3 วัน (ไม่ sync เพราะ Tailscale ดับ → DNS เพี้ยน
       → NTP UDP 123 timeout)

   แก้ทั้งหมด:
     - sed แก้ MTU 1350 → 1438 + beat 30ms → 50ms (พร้อม backup)
     - manual set Pi clock จาก laptop time (NTP ผ่าน gt0 ไม่ผ่าน — UDP 123
       ถูก block somewhere; ทีหลังเมื่อ tunnel ทำงานเต็ม Tailscale ค่อย sync เอง)
     - tailscale up --accept-dns=false → กลับมาออนไลน์ 100.82.150.4

   Hardware cutover — Pi รับช่วงต่อจาก Mini PC:
     - stop PC, ย้าย USB ASIX อีกตัว + LAN cable ไป Pi, ปิด PC
     - clients re-DHCP ผ่าน Pi's eth0 ภายใน ~30s
     - รอบแรกหลังย้าย eth2 ยังโชว์ NO-CARRIER (USB เสียบแต่ไม่มีสาย
       Ethernet) — ตรวจพบว่าสาย ISP B เสียบไม่แน่น

   เปรียบเทียบ Pi (rate 200m) vs Mini PC (rate 500m) — Pi ชนะทุก case:

              PC (500m)   Pi (200m)   Δ
     down p1     5.4        41.3      +665%   ← 8 เท่า!
     down p4    21.3        41.5       +95%
     down p8    25.9        43.1       +66%
     up   p1    42.0        46.9       +12%
     up   p8    39.9        62.7       +57%

   สาเหตุ: rate cap เล็กกว่า → queue ไม่ล้น → loss ต่ำกว่า
   (PC paths เคยมี RX-LOSS 0.78% ส่วน Pi 0% ระหว่าง bench)
   ตรงกับสูตร Mathis: throughput TCP แปรผกผันกับ √loss

   บันทึกไว้ใน bench/results/COMPARE-PC-vs-Pi-20260525.{md,txt}
   พร้อมอ้างหลักฐาน + Mathis prediction match กับตัวเลขจริง

3. Verify Bug 23 + ทดลอง Workarounds (ช่วงเย็น)
   ─────────────────────────────────────────────────────────────────
   ทำ controlled test (ทาง software, ไม่ต้องถอดสาย) — ตั้ง pref 0/1
   เพื่อ disable ทีละ path:

              Bonded   ISP A only   ISP B only
     up   p1    5.5       11.0        17.5      ← B alone 3× bonded
     down p1   10.1       13.9        30.1      ← B alone 3× bonded
     up   p8   38.5       43.8        28.5
     retx     2906       1032          290      ← B alone 10× cleaner

   Confirm 100% ว่า bonding ทำให้ TCP ช้ากว่า ISP เดียว
   เป็น "reorder penalty" ตรงตามที่ Bug 23 ระบุไว้ตั้งแต่ต้น

   เสนอ Active/Backup mode (ISP B primary, ISP A backup) — user reject
   ทันที "เราต้องการ Bandwidth Bonding มากๆ" → บันทึก preference ไว้
   เพื่อ session หน้าไม่ต้องเสนอซ้ำ

   ทดลอง Workaround 2 ทาง:

   Option β — Asymmetric rate weighting (ISP B 300m, ISP A 100m):
     hypothesis: glorytun-mud split proportional → ส่งไป B มากกว่า
     → reorder น้อยลง ผลที่ได้:
       - up p1: 5.5 → 1.7 Mbps (-69%)
       - up p8: 38.5 → 10.3 Mbps (-73%)
       - ISP B RX-LOSS spike เป็น 4.31%
     เข้าใจผิด — glorytun ไม่ split proportional, มัน push ตาม rate
     ที่ตั้ง → ตั้ง 300m แต่ ISP B รับไม่ไหว → loss เพิ่ม → Revert

   Option α — losslimit 5% (auto-disable path เมื่อ loss สูง):
     หวังว่าจะช่วยตอน burst loss monitor 60 วินาที ผลที่ได้:
       - path B ที่เคยมี RX-LOSS 4.31% ยังโชว์ "running" ไม่ถูก disable
         เพราะ glorytun ใช้ running-average ของช่วง 10s ล่าสุด ไม่ใช่
         cumulative
       - ปกติ loss ~0% → losslimit ไม่ kick
     losslimit ช่วยแค่ตอน ISP outage event ไม่ช่วยแก้ Bug 23 → Revert

   ข้อสรุป Bug 23: ไม่มี glorytun config ใดที่จะแก้ reorder penalty ได้
   ต้องเปลี่ยน architecture (OpenMPTCPRouter หรือ patch glorytun source
   ให้ทำ per-flow hashing) เก็บไว้ดำเนินการ session หน้า

   อัปเดต CLAUDE.md ให้ตรงกับ production state ปัจจุบัน:
     - Architecture diagram: miniPC → Pi 4
     - Active machine, Tailscale state, SSH aliases
     - เพิ่ม Session 2026-05-25 พร้อมตัวเลข bench Pi vs PC +
       workaround ที่ลองแล้วไม่ work
     - update "🔜 งานต่อไป" ให้สะท้อนว่าเหลือแต่ architectural changes

■ ปัญหาที่พบและแนวทางแก้ไข
────────────────────────────────────────────────────────────────────────

  ปัญหา : LAN noise สูง — variance ±20–30% ระหว่างชั่วโมง
  วิเคราะห์: ครอบครัวใช้ tunnel 7–8 client พร้อมกัน ทำให้ A/B test
             1-byte MTU difference (1438 vs 1439) อ่านไม่ออก
  แก้ไข : ต้องรัน A/B test back-to-back ทันที (ห่างกัน 25 นาที
             ยังต่างกัน 50%+ จาก noise) session หน้าถ้า tune ละเอียด
             ต้องรันตอนดึกที่ household idle

  ปัญหา : glorytun MTU 2 ชั้น — link MTU กับ internal MTU ทำงานต่างกัน
  วิเคราะห์: glorytun-mud probe internal MTU อัตโนมัติ (= 1442) และ
             ไม่ยอมให้ override — ต่างจาก link MTU ที่ตั้งผ่าน ip link set
  แก้ไข : ยอมรับว่า internal MTU = 1442 เปลี่ยนไม่ได้ แค่ตั้ง link
             MTU 1438 ให้ MSS clamping ทำงาน ก็พอ

  ปัญหา : Pi หาบน network ไม่เจอ — scan ทุก subnet แล้วไม่พบ
  วิเคราะห์: user ถอด USB ASIX adapter ออกจาก Mini PC ไปเสียบ Pi
             Pi ได้ DHCP IP เดิม (.6) เพราะ MAC adapter เดียวกัน
             ทำให้ IP ไม่ตรงกับที่คาด
  แก้ไข : user ช่วยบอกว่าน่าจะอยู่ .6 เพราะ MAC คุ้น — SSH ผ่านทันที
             เรียนรู้ว่า user observation มีค่า ควรถามก่อน scan เอง

  ปัญหา : glorytun reset link MTU กลับ 1442 หลัง service restart
  วิเคราะห์: glorytun probe MTU ตอน start และ override ค่าที่ตั้งไว้
  แก้ไข : ต้อง stop sync timer ก่อน แล้วตั้ง MTU 1438 หลัง glorytun start

  ปัญหา : Pi clock เพี้ยน 3 วัน
  วิเคราะห์: Tailscale พัง → DNS fail → NTP UDP 123 timeout loop
             ทำให้ไม่ได้ sync เวลานาน 3 วัน
  แก้ไข : manual set clock จาก laptop time ก่อน รอ Tailscale
             ขึ้นมาออนไลน์แล้วค่อย sync เอง (NTP UDP 123 ยังถูก block)

  ปัญหา : Asymmetric rate weighting ทำให้ loss spike ไม่ได้ช่วย
  วิเคราะห์: เข้าใจผิดว่า glorytun-mud split proportional ตาม rate
             ความจริง glorytun push ตาม target rate → ตั้ง 300m แต่
             ISP B รับไม่ไหว → loss เพิ่ม
  แก้ไข : เรียนรู้ algorithm จริงและบันทึกใน CLAUDE.md เพื่อไม่ลองซ้ำ

  ปัญหา : ISP B สาย Ethernet หลวมรอบแรกหลังย้าย hardware
  วิเคราะห์: สาย Ethernet ของ ISP B เสียบไม่แน่นหลัง cutover
  แก้ไข : user ตรวจสอบและเสียบใหม่ให้แน่น eth2 กลับมา carrier ปกติ

1. ติดตั้ง OpenMPTCPRouter (OMR) บน Mini PC อีกเครื่อง (ช่วงเช้า)
   ─────────────────────────────────────────────────────────────────
   Bug 23 (TCP single-stream slow over bonded tunnel) ยังเป็น architectural
   limitation ที่ glorytun-mud แก้ไม่ได้ ทางเลือกที่จดไว้ใน CLAUDE.md
   คือเปลี่ยนไปใช้ OMR ที่ทำ real MPTCP per-flow bonding (ไม่ใช่
   packet-level reorder แบบ glorytun) จึงเตรียม Mini PC อีกเครื่องมาลง
   OMR เป็น test bed แยกออกจากระบบ production ของ Pi 4

   ทำให้สามารถเปรียบเทียบทั้ง 2 แนวทางได้ในสภาพแวดล้อมจริงโดยไม่กระทบ
   ของเดิม และยังเก็บ Pi 4 ไว้เป็น primary ที่ทำงานต่อเนื่อง

2. แก้ Bug 27 (Clock Skew) บน Pi + วางระบบป้องกันระยะยาว (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   พบว่า Tailscale ของ Pi เข้าไม่ได้ — อาการเดิม (key sha256 ตรง,
   glorytun version ตรง, cipher ตรง แต่ tunnel ไม่ handshake) จึงเข้า
   ทาง LAN ที่ IP 192.168.1.2

     ผลตรวจ: Pi clock ช้ากว่า server 3 ชั่วโมง 7 นาที
     → glorytun-mud silently drop packet เพราะ timestamp นอก replay window

   แก้ทันที:
     SERVER_TIME=$(ssh glorytun-server 'date -u +"%Y-%m-%d %H:%M:%S"')
     ssh dtc@192.168.1.2 "sudo date -u -s '$SERVER_TIME'"
     sudo systemctl restart glorytun-pi.service

   Tunnel กลับมาภายใน 10 วินาที แต่ Tailscale ยัง "logged out" ต้อง
   restart tailscaled + tailscale up อีกครั้งจึงกลับมา 100.82.150.4

   เพราะปัญหานี้จะกลับมาทุกครั้งที่ Pi reboot (ไม่มี RTC battery +
   NTP UDP 123 ถูก ISP block) จึงวางระบบป้องกันถาวร 2 ชั้น:

   ชั้นที่ 1 — Boot-time: htpdate ผ่าน HTTPS
     สร้าง htpdate-boot.service บน Pi เป็น one-shot รัน
     Before=glorytun-pi.service ดึงเวลาจาก HTTPS Date header ของ
     google.com / cloudflare.com / apple.com ผ่าน port 443
     (ISP ไม่เคย block) accuracy ~1 วินาที อยู่ใน replay window ของ glorytun

   ชั้นที่ 2 — Runtime: chrony ผ่าน Tailscale ไป server
     ติดตั้ง chrony บน server + เพิ่ม "allow 100.64.0.0/10" ใน chrony.conf
     เพื่อ serve NTP ให้ subnet Tailscale (verify ผ่าน tcpdump)
     ติดตั้ง chrony บน Pi + ใส่ "server 100.65.195.27 iburst" ใน chrony.conf
     เลือก Tailscale IP เพราะไม่ถูก ISP block

   เพิ่ม drop-in /etc/systemd/system/glorytun-server.service.d/wait-for-time.conf
   บน server ให้ After=chrony.service time-sync.target กัน race condition
   ตอน server reboot โดยไม่ต้อง restart tunnel ที่รันอยู่

   ทดสอบหลังแก้:

   ── ส่วนที่ 2: Glorytun Channel Bonding Router ─────────────────────

   (1.10) ปัญหาที่ต้องการแก้ (ก่อนมีระบบ)
     - Unstable Connection Quality: ISP เดียวส่งผลกระทบกับ Video Call
       ต้องการ multi-path เพื่อกระจาย risk
     - Wasted Bandwidth: มีอินเทอร์เน็ต 2 เส้น แต่ใช้ได้เพียงเส้นเดียว
     - No Auto Failover: เมื่อเส้นหลักหลุด ต้องสลับด้วยมือทุกครั้ง
     - No Auto-Recovery: ระบบไม่กลับมาเองหลัง WAN เปลี่ยน IP, Reboot,
       หรือ Hotplug

   (1.11) Channel Bonding Architecture Overview
     - Raspberry Pi 4 (hostname: DTC) เป็น Central Bonding Node
       รับ WAN 2 เส้นผ่าน eth1 (ISP A, dynamic IP) + eth2 (ISP B, dynamic IP)
     - สร้าง Glorytun UDP Tunnel (port 65001, chacha20poly1305)
       ไปยัง VPN Server TH (61.91.251.238)
     - แจก IP อัตโนมัติให้ Client ผ่าน eth0 (Range 10.255.255.10–200)
     - Security Layer: fail2ban, nftables, pcap capture, logrotate
     - Backup: restic Daily 02:00, Retention 7d/4w/3m, NVMe 931GB

   (1.12) Phase 1–2: Channel Bonding + Router Setup
     - Glorytun + Watchdog: Service พร้อม Auto-restart รักษา Tunnel ตลอดเวลา
     - Policy Routing: แยก Routing Table eth1 → table 100, eth2 → table 101
       Rate Fixed tx/rx 100m ทั้ง 2 ทิศทาง
     - dnsmasq + nftables: แจก DHCP + DNS อัตโนมัติบน eth0, FORWARD
       eth0 ↔ gt0 พร้อม MSS Clamping และ NAT Masquerade 10.255.255.0/24

   (1.13) Phase 3: Auto-Recovery System
     - NetworkManager wan-auto: Profile แบบ multi-connect รองรับทุก WAN
       Interface โดยไม่ต้องตั้งค่าเพิ่ม
     - NM Dispatcher: อัปเดต Routing + Path อัตโนมัติทันทีเมื่อ IP เปลี่ยน
     - glorytun-sync.timer: ทำงานทุก 5 วินาที ตรวจสอบและ sync สถานะ Tunnel
     - Auto-Recovery ทุกกรณี: Reboot / Hotplug / IP Change → ระบบกลับมา
       เองอัตโนมัติโดยไม่ต้องแทรกแซง

   (1.14) Phase 4–5: Security Hardening + Backup
     - fail2ban: maxretry 10 / 30 min / ban 1h (nftables backend)
     - SSH: port 22 → 4822, ปิด PasswordAuthentication
     - nftables: DROP + log ทุก connection บน port 22
     - pcap capture gt0: snaplen 96 bytes, max 590GB
     - logrotate: daily ตี 1, จำกัด 600GB รวม
     - restic Full Backup ทุกวัน ตี 2, Retention 7d/4w/3m,
       LVM Expansion 100GB → 700GB, NVMe ความจุรวม 931GB

   (1.15) สรุปผลงาน + Next Steps
     สิ่งที่ทำได้สำเร็จ:
       - Channel Bonding รวม 2 เส้น
       - Auto-Failover 5–10 วินาที ไม่หลุด
       - Auto-Recovery ทุกกรณี (Reboot/Hotplug/IP Change)
       - Security + Backup (fail2ban, pcap, restic, LVM)
       - ระบบพร้อม Production Use — ผ่าน Reboot Test 10/10 ครั้ง
     Next Steps:
       - เพิ่ม Monitoring Dashboard (Grafana + Prometheus)
       - ปรับปรุง Alerting ผ่าน Telegram/Email
       - พิจารณา IPv6 Support ใน Tunnel

■ ปัญหาที่พบและแนวทางแก้ไข
────────────────────────────────────────────────────────────────────────

  ปัญหา : Pi clock ช้ากว่า server 3 ชั่วโมง 7 นาที ทำให้ tunnel handshake
           silently fail (glorytun drop packet ที่ timestamp นอก replay window)
  วิเคราะห์: Pi ไม่มี RTC battery + NTP UDP 123 ถูก ISP block → เวลาไม่ sync
             ตั้งแต่ครั้งก่อนที่ Tailscale พัง
  แก้ไข : sync เวลาด้วยมือทันที → ติดตั้งระบบ 2 ชั้น (htpdate HTTPS boot +
            chrony Tailscale runtime)

  ปัญหา : Tailscale ของ Pi ขึ้น "logged out" หลัง tunnel กลับมา
  วิเคราะห์: network unreachable ผ่าน IPv6 ระหว่างที่ tunnel ดับ ทำให้
             tailscaled ออก session
  แก้ไข : systemctl restart tailscaled → tailscale up --accept-dns=false

  ปัญหา : chrony บน server หลัง install ใหม่ ไม่ฟัง UDP 123 ทันที
  วิเคราะห์: ต้อง restart service หลังเพิ่ม "allow" rule ใน chrony.conf
             จึงจะ bind port
  แก้ไข : sudo systemctl restart chrony หลังแก้ config

  ปัญหา : htpdate บน server คำนวณ offset เพี้ยน ขึ้น "Setting -1779801834
           seconds" (พยายามตั้งเวลาเป็นปี 1970) เมื่อ apple.com timeout
  วิเคราะห์: offset เพี้ยนเมื่อ target host timeout เพียง 1 ใน 3 ตัว
  แก้ไข : ตัด htpdate ออกจาก server เพราะ x86 มี CMOS battery + NTP
            ไม่ถูก block อยู่แล้ว ใช้ chrony อย่างเดียวพอ ลด attack surface

3. Rewrite Reverse SSH Tunnel เป็น procd-based + Auto-Start on Boot
   ─────────────────────────────────────────────────────────────────
   Pi มี script /root/reverse-tunnel.sh อยู่แล้ว (ssh -R 9090:localhost:80
   จาก Pi → server port 65022) แต่ init script เดิมไม่ auto-start
   หลัง reboot

   ตรวจ init script เดิม:
     #!/bin/sh /etc/rc.common
     START=99 / STOP=10
     start() { sleep 20; /root/reverse-tunnel.sh & }
     stop()  { killall ssh 2>/dev/null }   ← อันตราย! ฆ่า ssh ทุก process

   ปัญหา:
     - ไม่ใช้ procd → ไม่มี respawn เมื่อ ssh ตายกลางทาง
     - stop() ใช้ killall ssh → กระทบทุก session รวมถึงของผู้ใช้
     - มี duplicate processes 2 ตัวค้างจากการรัน script ซ้ำ

   Rewrite เป็น procd-based:
     USE_PROCD=1
     start_service() → procd_open_instance
       command: /usr/bin/ssh
         -i /root/.ssh/id_ed25519
         -R 9090:localhost:80 -p 65022
         -o ServerAliveInterval=15
         -o ServerAliveCountMax=3
         -o ExitOnForwardFailure=yes
         -o StrictHostKeyChecking=no
         -o BatchMode=yes
         -N vpnserver@125.25.38.138
       procd_set_param respawn 10 5 0
     procd_close_instance

   chmod +x → enable → restart

   ผล:
     - procd-managed: respawn 10s threshold, 5s delay, ไม่จำกัด retry
     - ExitOnForwardFailure=yes → ssh exit ทันทีเมื่อ bind port พัง
       → procd เริ่มใหม่อัตโนมัติ
     - rc.d symlinks: S99reverse-tunnel + K10reverse-tunnel → auto-start
       on boot ✅
     - ทดสอบ kill -9 process → procd respawn ภายใน 5 วินาที ✅

4. Diagnose Zombie sshd-session บน Server หลัง Pi Reboot
   ─────────────────────────────────────────────────────────────────
   User ถอด-เสียบ Pi เพื่อทดสอบ resilience → รอ 10+ นาที server ยัง
   เปิด localhost:9090 ไม่ได้

   Pi side log:
     ssh[xxxx]: Remote TCP forward request failed (port 9090 -> localhost:80)
   = ssh ต่อ server ได้แต่ server ปฏิเสธ bind port 9090
     → ExitOnForwardFailure=yes → exit → procd respawn → fail loop

   Server side ตรวจ:
     sudo lsof -i :9090
     sshd-session 2960097 vpnserver  LISTEN 127.0.0.1:9090
     sshd-session 2960097 vpnserver  CLOSE_WAIT (16 connections!)

   = sshd-session เก่า (จาก tunnel รอบก่อน reboot Pi) ยึด port 9090
     ค้าง + CLOSE_WAIT 16 ตัวจาก Firefox ที่เปิด localhost:9090

   แก้: kill pid 2960097 → Pi procd respawn ภายใน 10 วินาที →
   bind 9090 สำเร็จ ✅

   แนะนำป้องกัน zombie กลับมา — เพิ่ม sshd config บน server:
     sudo tee /etc/ssh/sshd_config.d/timeout.conf << EOF
     ClientAliveInterval 30
     ClientAliveCountMax 3
     TCPKeepAlive yes
     EOF
     sudo systemctl reload ssh

   → ภายใน ~90s sshd detect client หาย → ปิด session อัตโนมัติ
   → port 9090 ว่าง → Pi reconnect ได้ทันที
   (user รับทราบ แต่ยังไม่ได้ apply วันนี้)

  วิเคราะห์: OMR เก็บ string ทั้ง space → script parse path พัง
  แก้ไข : uci set openmptcprouter.vps.ip='125.25.38.138' (ไม่มี space)
            + uci commit + restart openmptcprouter-vps service

  ปัญหา : Proxy mismatch — Pi default ใช้ shadowsocks-rust แต่ server
           เปิด shadowsocks-go → key ไม่ match → ฝั่ง Pi crash loop
  วิเคราะห์: OMR factory image ตั้ง ss-rust เป็น default แต่ server
             ติดตั้งมาพร้อม ss-go → ต้องตั้งให้ตรงกัน
  แก้ไข : ยังไม่แก้วันนี้ — แผนพรุ่งนี้เข้า Web UI ตั้ง Proxy tab
            ให้ Pi ใช้ ss-go ให้ตรงกับ server

  ปัญหา : Legacy init script ใช้ killall ssh ใน stop() กระทบ
           ssh session อื่น ๆ ทั้งหมด รวมถึง session ที่ใช้งานอยู่
  วิเคราะห์: ไม่มี scope จำกัด — ฆ่า process ssh ทุกตัวบนระบบ
  แก้ไข : เปลี่ยนเป็น procd-based ให้ procd จัดการ kill เฉพาะ
            instance ของ service ไม่กระทบ session อื่น

  ปัญหา : Zombie sshd-session บน server ยึด port 9090 ค้าง 10+ นาที
           หลัง Pi reboot เพราะ sshd ไม่ detect client disconnect
  วิเคราะห์: ไม่มี ClientAliveInterval → sshd ไม่รู้ว่า client หาย
             → session ค้าง → port ว่างไม่ได้
  แก้ไข : kill PID zombie สำหรับรอบนี้ + แนะนำเพิ่ม
            ClientAliveInterval=30 / ClientAliveCountMax=3 ใน
            /etc/ssh/sshd_config.d/timeout.conf บน server

  ปัญหา : scp ไปยัง OpenWRT Pi ใช้ SFTP protocol แต่ dropbear
           ไม่มี sftp-server → transfer ล้มเหลว
  วิเคราะห์: scp ใหม่ default เป็น SFTP แต่ dropbear ไม่รองรับ
  แก้ไข : ใช้ flag scp -O บังคับ legacy SCP protocol แทน

1. Merge maevVersion เข้า main + เตรียม Requirements สำหรับ Jetson (ช่วงเช้า)
   ─────────────────────────────────────────────────────────────────
   Push branch maevVersion ขึ้น remote แล้ว merge เข้า main แบบ merge commit
   (--no-ff) รวมงาน Version 14–17 ทั้งหมด (JWT auth, offline queue,
   user management, watchdog monotonic fix) เข้า main สำเร็จ
   (111 ไฟล์, ~16,000 บรรทัด)

   จากนั้นตรวจสอบ requirements.txt เพื่อเตรียมลงระบบบน NVIDIA Jetson Orin Nano
   พบว่า requirements.txt เดิมเป็น pip freeze จากเครื่อง x86_64 + GPU desktop
   ใช้บน Jetson (aarch64/JetPack) ไม่ได้ — torch+cu126, nvidia-*-cu12,
   onnxruntime-gpu (PyPI) เป็น x86 ทั้งหมด

   วิเคราะห์แล้วพบว่าโค้ดจริงใช้เพียง cv2, insightface, onnxruntime, mediapipe,
   fastapi stack, psycopg และ auth libs ส่วน torch/tensorflow ติดมาเพราะด่าน 6
   MiniFASNet (DeepFace) เท่านั้น จึงสร้าง requirements-jetson.txt แยก
   พร้อมคู่มือติดตั้งสำหรับ Jetson โดยเฉพาะ

2. Deploy ระบบลง Jetson Orin Nano (JetPack 6.2) ครบทั้งระบบ (ช่วงเช้า-บ่าย)
   ─────────────────────────────────────────────────────────────────
   SSH เข้า Jetson (ตั้ง SSH key ก่อน) สำรวจสเปค:
     JetPack 6.2 (L4T R36.4.7), Ubuntu 22.04, Python 3.10, CUDA 12.6, aarch64,
     RAM 7.4 GB

   ติดตั้งทีละขั้นตอน:
     - onnxruntime-gpu 1.23.0 + mediapipe 0.10.14 จาก jetson-ai-lab.io/jp6/cu126
     - แก้ปัญหา mediapipe ดึง numpy 2.x มา (insightface ต้อง <2)
       → downgrade numpy==1.26.4 + ถอน opencv ที่ซ้อนกัน เหลือ
       opencv-contrib-python-headless
     - ตั้ง FAS_ENABLED=False (ตัดด่าน 6 MiniFASNet ที่ต้องใช้ torch/tensorflow)
     - PostgreSQL local + migrations/setup_db.sql + admin user (bootstrap)
     - copy encodings.pkl + .env + สร้าง db_config.json
     - ลด cameras.json เหลือ IP cam ตัวเดียว เนื่องจาก 4 InsightFace instance
       พร้อมกันทำให้เกิด GPU OOM (CUBLAS_STATUS_ALLOC_FAILED) บน Orin Nano
     - nginx + build static (deploy ที่ /var/www/facereg) + แก้ config เพิ่ม
       location /attendance + /person → api_backend:8000
       (เดิมขาด ทำให้ Dashboard พัง)

   ทดสอบผ่าน: InsightFace บน GPU 19 FPS, ทุก endpoint ตอบ 200,
   START spawn main+api สำเร็จ เข้าเว็บที่ http://192.168.1.101 ได้

3. ฟีเจอร์ใหม่ — 3 โหมดการทำงานต่อกล้อง (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   ออกแบบให้แต่ละกล้องเลือกโหมดได้และ admin สลับได้ผ่าน Web UI:
     - faceatten : ระบบเดิม (oval guide + liveness + บันทึกลงเวลา)
     - detect    : ตรวจจับ + ระบุตัวตน แสดงข้อมูลคน แต่ไม่ liveness/
                   ไม่บันทึก/ไม่มี oval
     - cctv      : ดูภาพสดอย่างเดียว ไม่ inference
                   (ข้ามโหลด InsightFace ประหยัด GPU)

   ไฟล์ที่แก้ไข:
     - config.py         — เพิ่ม CAMERA_MODES
     - main.py           — run_camera แตกกิ่งตาม mode + ข้ามโหลด InsightFace
                           ถ้า cctv
     - stream_server.py  — mode ใน config + endpoint
                           POST /cameras/config/{id}/mode
                           (เลี่ยงปัญหา URL ถูก mask)
     - LiveCam.jsx       — dropdown โหมด + mode switcher บนการ์ด

   ทดสอบ 3 โหมดบน Jetson: cctv FPS พุ่ง 44.9 (vs faceatten 7.7)
   เพราะไม่ inference, detect ไม่บันทึกลงเวลาจริง (attendance count ไม่เพิ่ม)

4. แก้บั๊กการสลับโหมดขณะกล้องทำงาน (ช่วงบ่าย)
   ─────────────────────────────────────────────────────────────────
   บั๊ก 1: สลับโหมดขณะรัน → กล้องดับ (บางทีพากล้องอื่นดับด้วย)
     สาเหตุ: race condition — cam_start watcher spawn worker ใหม่ทันที
              โดยไม่รอ worker เก่าตาย → 2 worker แย่งกล้องตัวเดียว
              + graceful exit ออกกลางคันถ้ากล้องเดียว
     แก้ไข : main.py — cam_start watcher join worker เก่าก่อน spawn
              + graceful exit ไม่ออกถ้ามี cam_start flag ค้าง
              + front_end เรียก start อย่างเดียว (atomic)

   บั๊ก 2: IP cam เปลี่ยนไป CCTV → ทุกกล้องดับหมด (USB ไม่เป็น)
     สาเหตุจริง (เจอจาก log):
       "Assertion fctx->async_lock failed at
       libavcodec/pthread_frame.c:175"
       ThreadedCamera.release() เรียก cap.release() ขณะ reader thread
       ยัง cap.read() อยู่ → 2 thread แตะ FFmpeg context เดียวกัน
       → abort() ทั้ง process
       (USB ใช้ V4L2 ไม่มี frame-threading นี้จึงไม่เจอ)
     แก้ไข : camera.py — release() join reader thread ก่อนปล่อย capture

   reproduce + verify บนเครื่อง dev จริง (cam2 USB + cam3 IP):
   สลับโหมดแล้ว main ไม่ crash, กล้องอื่นไม่ดับ, assertion count = 0
