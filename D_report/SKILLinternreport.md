# รูปแบบรายงานประจำวันการฝึกงานเชิงเทคนิค (ภาษาไทย)

สกิลนี้ใช้เขียนรายงานประจำวันของการฝึกประสบการณ์วิชาชีพหรืองานเชิงเทคนิคในรูปแบบเฉพาะตัว ที่เน้นการบรรยายเชิงเล่าเรื่อง (narrative) แทนการใช้ bullet points โดยยังคงความแม่นยำทางเทคนิคไว้อย่างครบถ้วน

## โครงสร้างหลัก (บังคับใช้ตามลำดับ)

### 1. หัวเรื่อง (Header)
รูปแบบ: `วัน[ชื่อวัน]ที่ [วันที่] [เดือน] [พ.ศ.] (โปรเจกต์: [ชื่อโปรเจกต์])`

ตัวอย่าง:
- `วันจันทร์ที่ 25 พฤษภาคม 2569 (โปรเจกต์: Glorytun Channel Bonding Router)`
- `วันอังคารที่ 26 พฤษภาคม 2569 (โปรเจกต์: Glorytun Channel Bonding Router & Face Attendance System)`

กฎ:
- ใช้พุทธศักราช (พ.ศ.) เสมอ
- ชื่อโปรเจกต์เป็นภาษาอังกฤษคงรูป ไม่แปล
- หากมีหลายโปรเจกต์ในวันเดียวกัน ใช้เครื่องหมาย `&` คั่น

### 2. ส่วน "รายละเอียดงาน:"
- เขียนเป็น **ย่อหน้าเดียวยาวต่อเนื่อง** (single flowing paragraph) ไม่ใช้ bullet
- สรุปงานทั้งวันแบบ overview เน้นว่า "ทำอะไร" และ "เพื่ออะไร"
- ลักษณะประโยค: ยาว ใช้คำเชื่อม เช่น "พร้อมทั้ง" "รวมถึง" "นอกจากนี้" "อีกทั้ง"
- ใส่ศัพท์เทคนิคภาษาอังกฤษในวงเล็บกำกับคำไทย เช่น `สถาปัตยกรรมเครือข่าย (Network Architecture)`
- ความยาวประมาณ 3–6 บรรทัด

### 3. ส่วน "ปัญหาและแนวทางการแก้ไข:"
ประกอบด้วย "บล็อกปัญหา" หลายบล็อก โดยแต่ละบล็อกมีโครงสร้างจับคู่:

```
ปัญหา[คำอธิบายปัญหาเชิงพรรณนา] ([Technical Term ภาษาอังกฤษ]): [คำอธิบายอาการ สาเหตุ ค่าตัวเลขเชิงประจักษ์]
แนวทางแก้ไข: [ขั้นตอนที่ดำเนินการจริง พร้อมผลลัพธ์/เหตุผลทางเทคนิค]
```

กฎสำคัญของบล็อกปัญหา:
- ขึ้นต้นด้วยคำว่า "ปัญหา" เสมอ ตามด้วยคำอธิบายปัญหาแบบเล่าเรื่อง
- ใส่ technical term ภาษาอังกฤษในวงเล็บท้ายชื่อปัญหาเสมอ (เช่น `(Packet Reordering Penalty)`, `(LAN Noise Variance)`, `(Self-healing)`)
- หากมีหมายเลข bug ให้ระบุในชื่อปัญหา เช่น `ปัญหาข้อจำกัดของระบบ Glorytun (Bug 23) จาก...`
- คำอธิบายปัญหาต้องมี **ข้อมูลเชิงปริมาณ** เมื่อมีอยู่จริง (เช่น `120 Mbps`, `±20–30%`, `26 วินาที`, `44.7%`, `3 ชั่วโมง 7 นาที`)
- "แนวทางแก้ไข:" เขียนเป็นย่อหน้าเดียวต่อเนื่อง อธิบายสิ่งที่ทำพร้อมเหตุผลทางเทคนิค ไม่ใช้ bullet
- เว้นบรรทัดว่าง 1 บรรทัดระหว่างแต่ละบล็อกปัญหา

## แบบแผนภาษาและน้ำเสียง

### ระดับภาษา
- ทางการระดับรายงานวิชาการ/วิชาชีพ
- ใช้สรรพนามบุรุษที่ 1 น้อยที่สุด นิยมประโยคแบบ passive หรือใช้คำว่า "ดำเนินการ" "ตรวจพบ" "ทำการ"
- ห้ามใช้ภาษาพูดหรือคำสแลง

### ศัพท์เทคนิค (สำคัญมาก)
- **ใส่ศัพท์อังกฤษในวงเล็บกำกับเสมอ** หลังคำอธิบายภาษาไทยครั้งแรก
- ตัวอย่าง:
  - `การสลับลำดับข้อมูล (Packet Reordering Penalty)`
  - `อัตราการสูญเสียข้อมูลสูงสุด (losslimit)`
  - `ระบบโครงข่ายส่วนตัว (Tailscale IP)`
  - `ขอบเขตพื้นที่เสี่ยงภัยของระบบ (Attack Surface)`
- ชื่อโปรแกรม/ซอฟต์แวร์/โปรโตคอลคงรูปอังกฤษ: `Glorytun`, `chrony`, `htpdate`, `nftables`, `Tailscale`, `RTSP`, `H.264`, `ArcFace`, `ONNX Runtime`
- ค่าทางเทคนิค: คงรูปแบบสากล `120 Mbps`, `MTU 1442`, `MSS 1398`, `22–25 FPS`, `512 มิติ`

### คำเชื่อมที่ใช้บ่อย
- เปิดประโยค: "ตรวจพบว่า..." "พบว่า..." "เกิดปัญหา..." "ส่งผลให้..."
- เชื่อมเหตุผล: "เนื่องจาก..." "เพราะ..." "อันเป็นผลจาก..."
- เชื่อมขั้นตอน: "จากนั้น..." "พร้อมทั้ง..." "ต่อมา..." "ในขั้นถัดไป..."
- สรุป/ผล: "ส่งผลให้..." "ทำให้..." "ถือเป็น..." "ข้อสรุปคือ..."

## ตัวอย่างบล็อกปัญหามาตรฐาน

```
ปัญหาข้อจำกัดของระบบ Glorytun (Bug 23) จากการสลับลำดับข้อมูล (Packet Reordering Penalty): ตรวจพบว่าความเร็วผ่าน Bonded Tunnel แบบ TCP single-stream ถูกจำกัดอยู่ที่ประมาณ 120 Mbps แม้ทรัพยากรระบบของอุปกรณ์ Mini PC ยังเหลือเฟือ เนื่องจากเกิดปัญหาเรื่องการเรียงลำดับแพ็กเก็ตใหม่เมื่อส่งข้อมูลกระจายผ่าน 2 ช่องทางขนานกัน
แนวทางแก้ไข: ทำการทดสอบแนวทางแก้ไขเชิงซอฟต์แวร์ ทั้งวิธีปรับสัดส่วนแบนด์วิดท์แบบไม่สมมาตร (Asymmetric Rate Weighting) และการกำหนดอัตราการสูญเสียข้อมูลสูงสุด (losslimit) พบว่ายังไม่สามารถแก้ปัญหานี้ได้ ข้อสรุปในการแก้ไขปัญหาอย่างถาวรคือต้องทำการเปลี่ยนสถาปัตยกรรมเครือข่ายไปใช้ OpenMPTCPRouter ที่ทำ Per-flow Bonding หรือแก้ไขซอร์สโค้ดของ Glorytun เพื่อเพิ่มฟังก์ชัน Per-flow Hashing ในโอกาสต่อไป
```

วิเคราะห์โครงสร้างประโยค:
- ชื่อปัญหา: บรรยาย + (English term)
- อาการ: ค่าเชิงปริมาณ + บริบทอุปกรณ์
- สาเหตุ: อธิบายกลไกทางเทคนิค
- แนวทาง: สิ่งที่ลอง → ผล → ข้อสรุป/แผนถัดไป

## ข้อห้ามเด็ดขาด

1. **ห้ามใช้ bullet points หรือ numbered list** ในเนื้อหารายงาน (ทั้งส่วนรายละเอียดงานและส่วนปัญหา)
2. **ห้ามใช้หัวข้อย่อย markdown** (`##`, `###`) — ใช้เพียงคำนำหน้าหัวข้อภาษาไทยตามด้วยทวิภาค (`:`)
3. **ห้ามแปลชื่อเฉพาะของซอฟต์แวร์/โปรโตคอล/บริษัท** เป็นภาษาไทย
4. **ห้ามละข้อมูลเชิงปริมาณ** ที่ผู้ใช้ให้มา (ตัวเลข เปอร์เซ็นต์ หน่วย เวลา)
5. **ห้ามเปลี่ยนปี ค.ศ. เป็น พ.ศ. โดยอัตโนมัติเมื่อผู้ใช้ระบุชัด** หากผู้ใช้ระบุปี ค.ศ. ต้องสอบถามก่อน
6. **ห้ามใช้ภาษาอังกฤษเป็นเนื้อความหลัก** — ภาษาอังกฤษใช้เฉพาะในวงเล็บกำกับ ชื่อเฉพาะ หรือค่าทางเทคนิค

## ขั้นตอนการทำงานเมื่อได้รับคำขอ

1. ถ้าผู้ใช้ให้ข้อมูลดิบ/บันทึกย่อ ให้สแกนหา:
   - วันที่ + วัน + ชื่อโปรเจกต์
   - งานที่ทำในวัน (สำหรับส่วนรายละเอียดงาน)
   - ปัญหาแต่ละข้อ + อาการ + ค่าตัวเลข + วิธีแก้
2. หากข้อมูลใดขาดและจำเป็น (เช่น ไม่รู้ว่าเป็นวันอะไร หรือชื่อโปรเจกต์) ให้ถามก่อนเขียน
3. ถ้าข้อมูลมีปัญหาเดียว ก็ใช้บล็อกเดียวได้ ไม่ต้องเติมปัญหาสมมุติ
4. เขียนตามโครงสร้างทั้ง 3 ส่วน โดยรักษาน้ำเสียงทางการและการกำกับศัพท์อังกฤษอย่างสม่ำเสมอ
5. เมื่อเขียนเสร็จ ตรวจทาน checklist:
   - หัวเรื่องครบ (วัน + วันที่ + พ.ศ. + โปรเจกต์)
   - รายละเอียดงานเป็นย่อหน้าเดียว
   - ทุกบล็อกปัญหามีคู่ "ปัญหา..." + "แนวทางแก้ไข:"
   - มีค่าเชิงปริมาณครบทุกจุดที่ผู้ใช้ให้มา
   - ศัพท์เทคนิคในวงเล็บอังกฤษครบถ้วน

## รูปแบบผลลัพธ์

ส่งผลลัพธ์เป็น plain text ในแชตโดยตรง (ไม่ต้องสร้างไฟล์) เว้นแต่ผู้ใช้จะร้องขอเป็นไฟล์ (.docx, .md) อย่างชัดเจน หากเป็นรายงานหลายวันต่อเนื่อง ให้เว้นบรรทัดว่าง 1 บรรทัดระหว่างรายงานของแต่ละวัน
