        วันที่ 12 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองบริการ และลงมือพัฒนาระบบ Channel Bonding ต่อ โดยที่ในวันนี้ได้ย้าย Desktop Server จาก testing environment (192.168.1.0/24 ที่บ้าน) ไปยัง production environment ที่ออฟฟิศ (True Business Static IP 61.91.251.238/29) เครื่องได้รับ Public IP โดยตรงไม่ผ่าน NAT ของ router หลังย้ายพบปัญหา IP เก่าจากเครือข่ายเดิม (192.168.1.100/24) ค้างอยู่และมี default route ซ้ำกัน 2 อัน (proto static กับ proto dhcp) ทำให้ routing สับสนและออก Internet ไม่ได้ แก้ด้วยการ cleanup DHCP lease เก่า (dhclient -r) ลบ IP ที่ค้าง (ip addr del) และลบ default route ของ DHCP (ip route del) จากนั้นอัพเดท iptables NAT rules ให้ตรงกับ network ใหม่โดย flush POSTROUTING chain แล้วเพิ่ม MASQUERADE rule ใหม่

        นอกจากนี้ยังพบปัญหา typo ใน systemd service file ที่ระบุ cipher ว่า "chahcha" แทนที่จะเป็น "chacha" ทำให้ Glorytun reject option และ service เข้า restart loop กว่า 53 ครั้ง แก้ด้วย sed -i แล้ว daemon-reload จากนั้นทำการ build Glorytun บน Raspberry Pi 4 และทดสอบ connect ไปยัง Server พบปัญหา cipher mismatch ระหว่าง x86 Server ที่ใช้ AEGIS-256 (เพราะ CPU มี AES-NI) กับ Pi 4 ที่ใช้ ChaCha20-Poly1305 (เพราะ ARM ไม่มี AES-NI) แก้ด้วยการบังคับ flag "chacha" ทั้งสองฝั่งให้ตรงกัน หลังแก้ cipher paths แสดงสถานะ running ทั้ง 2 เส้น (192.168.1.4 ผ่าน eth0 และ 172.20.10.2 ผ่าน wlan0) อย่างไรก็ตาม ping ผ่าน tunnel ยังไม่ผ่าน ทำ tcpdump พบว่า ICMP echo request ออกจาก gt0 interface จริงแต่ไม่มี reply กลับมา ชี้ว่าปัญหาอยู่ฝั่ง Server ในส่วนของ kernel rp_filter หรือ iptables INPUT rules สิ้นวันได้เตรียม Claude Code สำหรับ automated debugging โดยสร้าง SSH key เฉพาะ (ed25519) สำหรับ cleanup ง่ายหลังเสร็จงาน และสร้าง CLAUDE.md ระบุ infrastructure context สำหรับ session debug ในวันถัดไป

        วันที่ 14 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองบริการ และลงมือพัฒนาระบบ Channel Bonding ต่อ โดยที่ในวันนี้ได้ต่อยอดจากที่ Channel Bonding พื้นฐานทำงานได้แล้ว โดยเป้าหมายคือทำให้ Raspberry Pi 4 ทำหน้าที่เป็น Router จริงๆ คือ Client เสียบสายเข้า eth0 แล้วได้รับ IP อัตโนมัติและออกอินเทอร์เน็ตผ่าน bonded tunnel ได้เลยโดยไม่ต้องตั้งค่าเพิ่มเติม เริ่มจากการขยาย tunnel subnet จาก /30 เป็น /24 ทั้งฝั่ง Pi และ Server จากนั้นกำหนด eth0 เป็น LAN gateway ที่ IP 10.255.255.254/24 และตั้ง NetworkManager ให้ eth0 เป็น unmanaged ถาวรเพื่อกัน NetworkManager ไม่ให้ยุ่งกับ interface นี้ ติดตั้ง dnsmasq เพื่อแจก DHCP บน eth0 พร้อมส่ง gateway และ DNS ให้ client อัตโนมัติ เปิด IP forwarding ผ่าน sysctl และสร้าง nftables FORWARD rule พร้อม MSS Clamping เพื่อแก้ปัญหา HTTPS และเว็บขนาดใหญ่โหลดไม่ได้ผ่าน tunnel ซึ่งเกิดจาก MTU mismatch ระหว่าง client (1500 bytes) กับ gt0 interface (1450 bytes) เพิ่ม policy routing table 200 ด้วย rule iif eth0 lookup 200 เพื่อให้ traffic ขาเข้าจาก client บน eth0 ออกทาง gt0 ได้ถูกต้อง

        ในส่วนของการรองรับ Dynamic IP ได้สร้าง NetworkManager profile ชื่อ wan-auto ที่ใช้ connection.multi-connect = multiple ทำให้ profile เดียวนี้สามารถ activate บน eth1, eth2, eth3 หรือ interface ใหม่ที่ไม่เคยเห็นมาก่อนได้พร้อมกัน พร้อมสร้าง NM dispatcher script ที่ /etc/NetworkManager/dispatcher.d/99-glorytun ซึ่งจะดึง IP จริงจาก interface ตั้ง policy routing และ register glorytun path อัตโนมัติทุกครั้งที่ interface เปลี่ยนสถานะ และตั้ง glorytun-sync.timer ทุก 5 วินาทีเป็น safety net กรณี dispatcher พลาด event หลัง reboot พบ 3 ปัญหาที่ต้องแก้ ได้แก่ dnsmasq start ก่อนที่ glorytun script สร้าง IP บน eth0, NetworkManager ดึง eth0 ไปใช้ทับ IP ที่ script ตั้งไว้ และ client ping gateway ไม่ได้เพราะ kernel เลือกส่ง ICMP reply เข้า tunnel แทน eth0 เนื่องจาก gt0 และ eth0 อยู่บน subnet เดียวกันและมี route metric เท่ากัน (metric 0 ทั้งคู่) แก้ครบทุกข้อด้วยการสร้าง systemd override (After=glorytun-pi.service), unmanaged-eth0.conf และปรับ gt0 route metric เป็น 200 ทดสอบ Channel Bonding วัดค่าจริงได้ประมาณ 72–84 Mbps เมื่อใช้ 2 เส้นพร้อมกัน และ failover อัตโนมัติภายใน 5–10 วินาทีเมื่อถอดสาย ยืนยันด้วย tcpdump ที่ Server ว่าเห็น packets จากทั้งสอง public IP พร้อมกัน ทดสอบ reboot 2 รอบผ่านครบทุก check

        วันที่ 15 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองบริการ และลงมือพัฒนาระบบ Channel Bonding ต่อ โดยที่ในวันนี้มุ่งเน้นเพิ่มความปลอดภัยและวางระบบ Logging ที่จัดการตัวเองได้ เริ่มจากการตรวจสอบ auth.log พบว่ามีการโจมตี SSH มากถึง 29,911 ครั้งในรอบ 5 วัน จาก 46 unique IP addresses โดย IP ที่โจมตีหนักสุดคือ 192.109.200.50 (1,593 ครั้งในวันเดียว) และ username ที่ถูกโจมตีหนักสุดคือ root (12,644 ครั้ง) จึงติดตั้ง fail2ban โดยพบปัญหาสำคัญว่า fail2ban ใช้ iptables เป็น default action แต่ Server ใช้ nftables โดยตรง ทำให้ ban command ล้มเหลวและ IP ที่ "ban" ไม่โดน block จริง แก้โดยเพิ่ม banaction = nftables-multiport ใน jail config หลังแก้แล้ว fail2ban สร้าง nftables set ชื่อ addr-set-sshd และ reject rule ได้ถูกต้อง ทดสอบยืนยัน 2 IPs โดน ban ทันที จากนั้นเปลี่ยน SSH port จาก 22 เป็น 4822 โดยทำอย่างระมัดระวัง (เพิ่ม port ใหม่ก่อน ทดสอบ SSH เข้าได้ แล้วค่อย remove port เก่า เพื่อป้องกัน lock ตัวเอง) พร้อมปิด PasswordAuthentication, PermitRootLogin no และ MaxAuthTries 3 เพิ่ม nftables rule ให้ drop ทุก packet ที่เข้า port 22 พร้อม log

        ในส่วน Log Management ได้ตั้งค่า logrotate สำหรับ log ทั้งหมดที่สำคัญ (auth, kern, syslog, daemon, dpkg, fail2ban, nftables-drop) โดย rotate daily ตี 1 maxsize 1GB และสร้าง log-size-limit.sh script ที่ตรวจ total size ของ /var/log ถ้าเกิน 600GB จะลบไฟล์เก่าออกอัตโนมัติ ตั้ง pcap-capture.service ให้บันทึก traffic บน gt0 interface ด้วย tcpdump (snaplen 96 bytes เพื่อเก็บแค่ header ไม่เก็บ payload, rotate ทุก 1GB, max 590 files) ระหว่างติดตั้งพบปัญหาสามด้านต่อเนื่องกัน ได้แก่ path ของ tcpdump binary ในระบุใน service file ผิด (ควรเป็น /usr/bin ไม่ใช่ /usr/sbin), permission denied บน pcap directory เพราะ tcpdump drop privileges ไปใช้ user "tcpdump" เอง และ traffic ของ Pi ไม่ผ่าน gt0 เพราะ Pi ส่ง traffic ตัวเองออกตรง WAN ต้องใช้ client จริงเสียบ eth0 เพื่อทดสอบจึงจะเห็น packet บน gt0 แก้ครบทุกข้อแล้ว ในด้าน Storage พบว่า root LV ถูก provision แค่ 100GB ทั้งที่ NVMe disk มี 931GB และ LVM VG มี free space 828GB จึงขยาย LV เป็น 700GB ด้วย lvextend และ resize2fs แบบ online ไม่ต้อง unmount ได้ disk ว่างเพิ่มจาก 81GB เป็น 647GB ติดตั้ง restic init backup repository รัน full backup ครั้งแรก (9.8GB) และตั้ง timer รันทุกวันตี 2 พร้อม retention policy สิ้นวันได้สร้างเอกสาร 3 ชิ้น ได้แก่ RESTORE-GUIDE.txt คู่มือ restore แบบ step-by-step, diagram-description.txt อธิบาย component ทุกชิ้นในภาพ network diagram และ user-manual.txt v2.0 ที่รวม manual เก่ากับของใหม่เป็นไฟล์เดียวพร้อมเพิ่มส่วน Security Layer, restic backup commands และ Windows SCP commands นอกจากนี้ยังตรวจพบข้อผิดพลาด 2 จุดในภาพ network diagram ที่ผู้ดูแลส่งมา ได้แก่ protocol ของ Glorytun ระบุว่า GRE แต่ที่ถูกต้องคือ UDP และ NAT direction ระบุว่า Inbound only แต่ที่ถูกต้องคือ NAT Masquerade ขาออก (Outbound)

ปัญหาและอุปสรรค์ที่พบ

  - OMR install script เพิ่ม Ubuntu Bionic/Impish repository ที่ถูกย้ายไป old-releases แล้วกลับเข้ามาทุกครั้งที่รัน ทำให้ apt update fail ด้วย 404 Not Found
  - OMR ต้องการ libmbedcrypto3 ซึ่ง Ubuntu 22.04 ไม่มี (มีแต่ libmbedcrypto7 ที่ ABI ไม่เข้ากัน)
  - Glorytun syntax ต่างจาก documentation หลายจุด ต้องอ่าน source code โดยตรง
  - Systemd service file มี typo "chahcha" ทำให้ Glorytun reject option และ service เข้า restart loop กว่า 53 ครั้ง
  - Cipher mismatch ระหว่าง x86 Server (AEGIS-256) กับ ARM Pi 4 (ChaCha20-Poly1305)
  - IP เก่าค้างและ default route ซ้ำ 2 อัน หลังย้าย Server ไปยัง production network
  - dnsmasq start ก่อนที่ glorytun script สร้าง IP บน eth0 ทำให้ fail ทุก reboot
  - NetworkManager ดึง eth0 ไปใช้ทับ IP ที่ script ตั้งไว้
  - Client ping gateway ไม่ได้เพราะ ICMP Redirect (route metric conflict ระหว่าง gt0 และ eth0 บน subnet เดียวกัน)
  - fail2ban ใช้ iptables เป็น default action ขณะที่ Server ใช้ nftables ทำให้ ban ไม่มีผลจริง
  - tcpdump binary อยู่ที่ /usr/bin ไม่ใช่ /usr/sbin และ pcap directory permission denied เพราะ tcpdump drop privileges เป็น user tcpdump
  - LVM root volume ถูก provision แค่ 100GB ทั้งที่ NVMe disk มี free space ถึง 828GB

แนวทางการแก้ปัญหาดังกล่าว แก้ไขได้โดย

  - Patch OMR script ด้วย comment out บรรทัดที่เพิ่ม repository ที่ล้าสมัย และเปลี่ยนแผนจาก OMR ไปใช้ Glorytun UDP standalone เพื่อหลีกเลี่ยง dependency hell
  - อ่าน source code โดยตรง (bind.c, path.c) เพื่อหา argument syntax ที่ถูกต้องของ Glorytun version 0.3.4
  - แก้ typo ด้วย sed -i แล้วรัน systemctl daemon-reload และ restart service
  - บังคับ flag "chacha" ทั้งสองฝั่งให้ cipher algorithm ตรงกัน
  - Cleanup DHCP lease เก่าด้วย dhclient -r พร้อม ip addr del และ ip route del
  - สร้าง systemd override ให้ dnsmasq รอ glorytun-pi.service ก่อนด้วย After= directive
  - สร้าง /etc/NetworkManager/conf.d/unmanaged-eth0.conf ตั้ง eth0 เป็น unmanaged ถาวร
  - ลบ gt0 route /24 แล้วเพิ่มใหม่ด้วย metric 200 ทำให้ eth0 (metric 0) ชนะ client traffic เสมอ
  - เพิ่ม banaction = nftables-multiport ใน fail2ban jail config และ restart fail2ban
  - แก้ service file path จาก /usr/sbin เป็น /usr/bin และ chown /var/log/pcap เป็น tcpdump:tcpdump
  - ขยาย LVM LV ด้วย lvextend -L 700G และ resize2fs แบบ online ไม่ต้อง unmount
