ประจำสัปดาห์ที่ 11 วันที่ 25 พฤษภาคม 2569 ถึง 29 พฤษภาคม 2569

        วันที่ 25 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองการศึกษา วิจัย และพัฒนา และปฏิบัติงานต่อในส่วนของโครงการเสริม Channel Bonding Router (glorytun) ซึ่งทำควบคู่กับโครงการหลัก โดยในวันนี้มุ่งแก้ไขปัญหาที่ค้างอยู่คือ TCP single-stream ผ่าน bonded tunnel ตันอยู่ที่ประมาณ 120 Mbps ทั้งที่ทรัพยากรของเครื่องยังว่างอยู่มาก เริ่มจากการสร้างชุดเครื่องมือทดสอบ (bench framework) เพื่อวัดประสิทธิภาพอย่างเป็นระบบก่อน ประกอบด้วยสคริปต์ทดสอบ TCP matrix หลายสตรีม การวัด byte counter ราย WAN ทุกวินาที และตัวสรุปผลเป็นเอกสาร เมื่อนำไปทดสอบบนเครื่องจริงพบข้อมูลสำคัญว่า glorytun กระจาย packet ลงทั้งสองเส้นทางอย่างละ 50 เปอร์เซ็นต์สมบูรณ์ และ tunnel รองรับ UDP ได้ถึงประมาณ 365-385 Mbps จึงตัดสมมติฐานเรื่อง packet ไปทางเดียวและขีดจำกัดของ tunnel ออกได้ จากนั้นทดลองปรับค่า rate cap และทดสอบ MTU sweep พบว่าเส้นทางจากเครื่องไปยังเซิร์ฟเวอร์ถูกจำกัด PMTU ที่ 1492 ซึ่งเป็นข้อจำกัดฝั่งผู้ให้บริการอินเทอร์เน็ตที่ไม่สามารถควบคุมได้

        วันที่ 26 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองการศึกษา วิจัย และพัฒนา และปฏิบัติงานต่อ โดยช่วงเช้าได้ติดตั้งระบบ OpenMPTCPRouter (OMR) บนเครื่อง Mini PC อีกเครื่องเพื่อใช้เป็นชุดทดสอบทางเลือกในการแก้ปัญหาดังกล่าว เนื่องจาก OMR ทำการรวมช่องสัญญาณแบบ per-flow ซึ่งต่างจาก glorytun ส่วนช่วงบ่ายพบปัญหาสำคัญคือนาฬิกาของเครื่อง Raspberry Pi ช้ากว่าเซิร์ฟเวอร์ 3 ชั่วโมง 7 นาที ทำให้ tunnel ไม่สามารถเชื่อมต่อได้เพราะ timestamp อยู่นอกช่วงที่ยอมรับ จึงแก้ไขโดยการตั้งเวลาด้วยมือก่อนแล้ววางระบบป้องกันถาวรสองชั้น ชั้นแรกใช้ htpdate ดึงเวลาผ่าน HTTPS ขณะบูตเครื่อง และชั้นที่สองใช้ chrony ซิงค์เวลาผ่าน Tailscale อย่างต่อเนื่อง เนื่องจากเครื่องไม่มีแบตเตอรี่นาฬิกาและพอร์ต NTP มาตรฐานถูกผู้ให้บริการบล็อก ปิดท้ายด้วยการเก็บบันทึกการใช้งานแบนด์วิดท์จริง 15 นาทีและจัดทำชุดเอกสารหลักฐานสำหรับการนำเสนอในวันถัดไป

        วันที่ 27 พฤษภาคม 2569 เข้าร่วมการประชุมศูนย์ในช่วงเช้าเพื่อรายงานความคืบหน้าของโครงการที่รับผิดชอบทั้งสองโครงการ คือระบบบันทึกเวลาเข้างาน-ออกงานด้วยการจดจำใบหน้า และโครงการ Channel Bonding จากนั้นในช่วงบ่ายดำเนินการย้ายระบบของ Raspberry Pi จาก glorytun ไปเป็น OMR เต็มรูปแบบ ขั้นตอนประกอบด้วยการเปิด SSH และแก้ไขไฟร์วอลล์บนเซิร์ฟเวอร์ OMR ตัวใหม่ การสำรองค่าตั้งทั้งหมดของ Pi ก่อนการ flash การเขียน OMR image ลงการ์ด SD และบูตเครื่องสำเร็จ ระหว่างทางพบปัญหาสองรายการ คือไฟร์วอลล์ของ OMR ปิดกั้น interface ของ Tailscale ทำให้เข้าผ่าน SSH ไม่ได้ และ image มาตรฐานของ OMR ตั้งค่าการ์ดเครือข่ายเป็นแบบ MACVLAN โหมด vepa ซึ่ง router ตามบ้านไม่รองรับทำให้ไม่ได้รับ IP จึงแก้ไขด้วยการปรับ config ให้ใช้การ์ดเครือข่ายโดยตรง

        วันที่ 28 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองการศึกษา วิจัย และพัฒนา และปฏิบัติงานต่อในการจับคู่ (pairing) ระหว่าง Raspberry Pi กับเซิร์ฟเวอร์ OMR ให้สำเร็จ ซึ่งต้องแก้ปัญหาหลายชั้น เริ่มจากการกรอกหมายเลข IP ในแบบฟอร์มเผลอใส่ช่องว่างนำหน้าทำให้สคริปต์ทำงานผิดพลาด ตามด้วยปัญหา proxy ที่ฝั่ง Pi กับเซิร์ฟเวอร์ใช้คนละชนิดทำให้กุญแจไม่ตรงกัน จากนั้นได้ปรับปรุงสคริปต์ reverse SSH tunnel จากแบบเดิมให้เป็นแบบ procd ที่มีการ respawn อัตโนมัติและเริ่มทำงานเองหลังรีบูต พร้อมแก้ปัญหา session ค้าง (zombie) บนเซิร์ฟเวอร์ที่ยึดพอร์ตไว้ และปิดท้ายด้วยการสำรองระบบของ Pi ทั้งหมดเพื่อใช้ในการกู้คืน

        วันที่ 29 พฤษภาคม 2569 เข้าร่วมการประชุมสภากาแฟในช่วงเช้า เพื่อฟังการรายงานความคืบหน้าของงานที่ปฏิบัติในช่วงที่ผ่านมา จากนั้นเดินทางไปประจำกองการศึกษา วิจัย และพัฒนา และกลับมาพัฒนาโปรแกรมระบบบันทึกเวลาเข้างาน-ออกงานด้วยการจดจำใบหน้าต่อ โดยในวันนี้เริ่มจากการรวมโค้ดสาขา maevVersion เข้าสู่สาขาหลัก จากนั้นนำระบบไปติดตั้งบนเครื่อง NVIDIA Jetson Orin Nano ซึ่งเป็นสถาปัตยกรรม ARM64 ที่ต่างจากเครื่องพัฒนาเดิม จึงต้องจัดการ dependency ใหม่ทั้งหมด ได้แก่การติดตั้ง onnxruntime-gpu และ mediapipe จากแหล่งเฉพาะของ Jetson การติดตั้งฐานข้อมูล PostgreSQL การตั้งค่า nginx เพื่อให้บริการหน้าเว็บ จนระบบรู้จำใบหน้าทำงานบน GPU ได้ที่ประมาณ 19 เฟรมต่อวินาที จากนั้นพัฒนาฟีเจอร์ใหม่ให้กล้องแต่ละตัวเลือกโหมดการทำงานได้สามแบบ คือโหมดบันทึกเวลาเต็มรูปแบบ โหมดตรวจจับแสดงข้อมูลอย่างเดียว และโหมด CCTV ที่ไม่ประมวลผลภาพเพื่อประหยัดทรัพยากร โดยผู้ดูแลระบบสามารถสลับโหมดได้ ในระหว่างการทดสอบพบข้อผิดพลาดสำคัญสองรายการ คือการสลับโหมดขณะระบบทำงานทำให้กล้องดับ และเมื่อเปลี่ยนกล้อง IP เป็นโหมด CCTV ทำให้ระบบหยุดทำงานทั้งหมด ซึ่งได้ตรวจสอบจนพบสาเหตุที่แท้จริงและแก้ไขเรียบร้อย รวมถึงปรับปรุงหน้าจอผู้ใช้หลายส่วน

ปัญหาและอุปสรรค์ที่พบ

  - TCP single-stream ผ่าน bonded tunnel ตันที่ประมาณ 120 Mbps โดยไม่ทราบสาเหตุชัดเจน
  - นาฬิกาของ Raspberry Pi ช้ากว่าเซิร์ฟเวอร์ 3 ชั่วโมง ทำให้ tunnel เชื่อมต่อไม่ได้ และจะกลับมาเกิดซ้ำทุกครั้งที่รีบูตเพราะไม่มีแบตเตอรี่นาฬิกาและพอร์ต NTP ถูกบล็อก
  - ไฟร์วอลล์ของ OMR ปิดกั้น interface ของ Tailscale ทำให้เข้าผ่าน SSH ไม่ได้
  - OMR image มาตรฐานตั้งค่าการ์ดเครือข่ายเป็น MACVLAN โหมด vepa ที่ router ตามบ้านไม่รองรับ ทำให้ไม่ได้รับ IP
  - การกรอก IP ในแบบฟอร์มมีช่องว่างนำหน้า และ proxy ของ Pi กับเซิร์ฟเวอร์เป็นคนละชนิด ทำให้ระบบเชื่อมต่อไม่สมบูรณ์
  - session ค้าง (zombie) บนเซิร์ฟเวอร์ยึดพอร์ตไว้หลัง Pi รีบูต ทำให้ reverse tunnel กลับมาไม่ได้
  - ชุดติดตั้ง dependency เดิมของระบบจดจำใบหน้าใช้กับเครื่อง Jetson (ARM64) ไม่ได้ และเมื่อเปิดกล้องหลายตัวพร้อมกันทำให้หน่วยความจำ GPU ไม่พอ
  - การสลับโหมดกล้องขณะระบบทำงานทำให้กล้องดับ และการเปลี่ยนกล้อง IP เป็นโหมด CCTV ทำให้โปรแกรมหยุดทำงานทั้งระบบ

แนวทางการแก้ปัญหาดังกล่าว แก้ไขได้โดย

  - สร้างชุดเครื่องมือทดสอบเพื่อวัดผลอย่างเป็นระบบ จนตัดสมมติฐานที่ไม่ใช่ออกได้ และพบว่าคอขวดอยู่ที่ผู้ให้บริการอินเทอร์เน็ต พร้อมเตรียมทางเลือก OMR ที่รวมช่องสัญญาณแบบ per-flow
  - ตั้งเวลาด้วยมือทันที แล้ววางระบบป้องกันถาวรสองชั้น คือ htpdate ผ่าน HTTPS ขณะบูต และ chrony ผ่าน Tailscale ขณะทำงาน
  - เพิ่มกฎ iptables ยอมรับ interface ของ Tailscale พร้อมสคริปต์ให้ทำงานซ้ำอัตโนมัติหลังรีบูต
  - ปรับ config ของ OMR ให้ใช้การ์ดเครือข่ายโดยตรงแทน MACVLAN
  - แก้ค่า IP ด้วยคำสั่งโดยตรงให้ถูกต้อง และวางแผนตั้ง proxy ทั้งสองฝั่งให้ตรงกัน
  - ปรับปรุงสคริปต์ reverse tunnel เป็นแบบ procd ที่ respawn เอง และแนะนำตั้งค่า ClientAliveInterval บนเซิร์ฟเวอร์เพื่อปิด session ค้างอัตโนมัติ
  - สร้างชุดติดตั้ง dependency เฉพาะสำหรับ Jetson และลดจำนวนกล้องที่ทำงานพร้อมกันให้เหมาะกับหน่วยความจำ GPU
  - แก้ไขลำดับการสร้างและปิด worker ของกล้องให้รอกันอย่างถูกต้อง และแก้ปัญหา library ของ FFmpeg ที่เข้าถึงทรัพยากรพร้อมกันจนโปรแกรมหยุดทำงาน
