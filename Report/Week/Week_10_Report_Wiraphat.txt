        ในช่วงบ่ายได้ดำเนินโครงการอีกอันที่ทำคู่กัน คือ glorytun channel-bonding router ซึ่งทำหน้าที่รวมเน็ตจาก ISP 2 เส้นเข้า tunnel ไปยัง server เพื่อให้ client ใช้ internet ผ่านการ bond โดยเดิม Raspberry Pi 4 ติดเพดาน CPU ที่ประมาณ 200 Mbps เพราะ chacha20 encrypt เป็น single-thread บน Cortex-A72 ที่ไม่มี crypto extension วันนี้ได้รับ mini PC ใหม่ (Intel Core i5-12500T, 12 cores พร้อม AES-NI และ AVX2, RAM 16 GB, Ubuntu 22.04.5 LTS) จึงเริ่ม migration เต็มรูปแบบ ตั้งแต่ติดตั้ง Tailscale บน PC ใหม่, build glorytun จาก source, copy keyfile จาก server backup, เขียน scripts สำหรับ PC ใหม่ (ปรับชื่อ interface จาก eth0/eth1/eth2 ของ Pi เป็น enp0s31f6/wan1/wan2 บน PC), ติด udev rules ให้ USB-Ethernet rename ตาม MAC address อัตโนมัติ และสร้าง systemd services glorytun-pc.service พร้อม glorytun-sync.timer และ cutover script

        ระหว่างทำ cutover (ย้ายสายจาก Pi ไป PC พร้อม stop Pi service และ start PC service) พบปัญหาซ้อนกัน 3 ตัวที่ต้องแก้ทันที ได้แก่ dnsmasq fail เพราะ port 53 ชนกับ systemd-resolved บน Ubuntu 22.04 (แก้โดยเพิ่ม listen-address, except-interface=lo และ bind-interfaces), enp0s31f6 ตั้ง IP ไม่ติดเพราะ netplan cloud-init มี dhcp4: true ทำให้ systemd-networkd พยายาม DHCP และ flush IP (แก้โดยเพิ่ม netplan override เป็น static), iperf3 fail บน server เพราะ UFW เปิดเฉพาะ port 22/tcp (แก้ชั่วคราวด้วย ufw allow port 5201) นอกจากนี้ยังค้นพบ Bug ใหม่ที่เป็น root cause ของปัญหา speed คือทดสอบ speed ผ่าน tunnel ได้แค่ 120-130 Mbps ทั้งที่ตั้ง rate 500m × 2 = 1 Gbps theoretical วัดด้วย iperf3 PC↔server (8 parallel streams) ได้ PC → server 64.6 Mbps พร้อม retransmits 1650 ครั้ง และ PC ← server 15.5 Mbps พร้อม retransmits 884 ครั้ง จำนวน retransmit ที่สูงนี้คือ smoking gun ของ TCP single-stream reorder penalty ของ channel bonding เพราะ glorytun ส่ง packet กระจาย 2 paths แบบ rate-based แต่ ISP A กับ B latency ไม่เท่ากัน packet จึง arrive ผิดลำดับ TCP เห็นเป็น packet loss ส่ง dup ACK และ cwnd ลด ทำให้ single-stream ตัน เป็น fundamental limitation ของ channel bonding กับ TCP ไม่ใช่ปัญหาของ hardware จึงตัดสินใจคงโหมด True Bonding ไว้ก่อน เพื่อให้ aggregate throughput สูงเมื่อใช้หลาย application พร้อมกัน แล้วยอม single-stream ตก โดยจะมาแก้ปัญหานี้ต่อในวันจันทร์ ในช่วงท้ายของวันได้อัปเดต CLAUDE.md เพิ่ม section Migration Pi 4 → Mini PC ครอบคลุม hardware spec, interface mapping, network backend, key files, bugs 20-23 ที่เจอ root cause พร้อม fix และ plan งานวันจันทร์

ปัญหาและอุปสรรค์ที่พบ

  - บัค auto-stop ของระบบ FaceReg ไม่ทำงาน ค้างมาจากสัปดาห์ก่อน วินิจฉัยผิดในตอนแรกว่าเป็น zombie process
  - watchdog thread crash เงียบทุก tick เพราะ _watchdog_loop() ลืม global declaration ของ _last_cam_active_ts
  - _last_cam_active_ts = time.time() ตอน /system/start ทำให้ระบบ auto-stop ตัวเองทันทีหลังกด Start ระหว่างกล้อง boot
  - _stop_api() ใช้ fuser fallback ทำให้ใน dev mode (concurrently) cascade kill ทุก process
  - LIVENESS_TIMEOUT ตัดก่อนได้ทำ finger challenge ถ้าคนกระพริบตานานเกินไป
  - หน้า Report export CSV/XLSX/PDF ขึ้น 401 เพราะ window.open() ไม่แนบ JWT
  - axios ใน attendance.js และ history.js ไม่แนบ JWT ทำให้ Dashboard/ประวัติ/รายงานโหลดไม่ได้
  - DB OFFLINE badge แสดงผิดเพราะ probe endpoint ไม่ส่ง token
  - ระบบดับเองหลัง 6 ชั่วโมงเมื่อผู้ใช้เปลี่ยน system clock เพราะ stream_server ใช้ time.time() (wallclock) สำหรับ duration measurement
  - main.py กับ stream_server เป็นคนละ process ทำให้ monotonic timestamp เปรียบเทียบ cross-process ไม่ได้
  - .gitignore pattern .env.* ดัก .env.example โดยไม่ตั้งใจ และ inline comment ในบรรทัด pattern ไม่ทำงาน
  - install_service.sh hardcode path/user ของผู้พัฒนา ทำให้ทีม deploy ใช้บนเครื่องอื่นไม่ได้
  - dnsmasq บน Ubuntu 22.04 fail เพราะ port 53 ชนกับ systemd-resolved
  - enp0s31f6 ตั้ง IP ไม่ติดเพราะ netplan cloud-init มี dhcp4: true แล้ว flush IP ทุกครั้ง
  - iperf3 ทดสอบ tunnel speed ล้มเหลวเพราะ UFW เปิดเฉพาะ port 22
  - speed test ผ่าน tunnel ติดที่ ~130 Mbps ทั้งที่ rate รวม 1 Gbps theoretical เพราะ TCP single-stream reorder penalty ของ channel bonding
