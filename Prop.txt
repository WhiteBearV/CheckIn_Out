ปัญหาที่ 5 — Screen Border False Positive จากกล้อง IP RTSP H.264
================================================================================

5.1 บริบทและหน้าที่ของด่านนี้
--------------------------------------------------------------------------------
ใน Anti-Spoofing Pipeline 7 ด่านของระบบ ด่านที่ 5 ชื่อว่า Screen Border
Detection ทำหน้าที่ป้องกันการโจมตีแบบ Replay Attack หรือ Photo Attack
ที่ผู้โจมตีใช้มือถือ/แท็บเล็ตเปิดรูปคนเป้าหมายแล้วชูให้กล้องดู

แนวคิดเดิมคือ: ถ้ามีคน "ถือของ" มาส่อง กล้องจะเห็นขอบสี่เหลี่ยมของจอ/เคส
อยู่รอบใบหน้า ด่านนี้จึงตรวจ 3 สัญญาณคู่กัน:

  1. Edge ratio ใน margin zone รอบใบหน้า — ถ้ามีเส้นตรงเยอะแสดงว่าน่าจะ
     เป็นขอบจอ
  2. Inner density — ความหนาแน่นเส้นในพื้นที่หน้า (จอ LCD มี pixel pattern
     หนาแน่นกว่าหน้าจริง)
  3. FFT analysis — วิเคราะห์ frequency spectrum เพื่อจับ moiré pattern
     ของจอ


5.2 อาการปัญหาที่เจอ
--------------------------------------------------------------------------------
หลังย้ายจาก USB webcam มาเป็น IP Camera RTSP
(rtsp://admin:@dmin123456@192.168.1.13:554/unicast/c1/s0/live) เริ่มเจอ:

  - คนจริงยืนหน้ากล้อง → ระบบบอกว่าเป็น "screen" → fail liveness
    → ไม่ลงเวลาให้
  - ตรวจจาก HUD พบว่า FFT score = 0.000 ตลอด แม้เป็นคนจริง 100%
  - เกิดต่อเนื่องครบ SCREEN_CONFIRM_SEC = 3.0 วิ → screen_ok = False
    ค้างถาวร


5.3 การวิเคราะห์สาเหตุเชิงลึก
--------------------------------------------------------------------------------
ดู liveness_engine.py:300-348 แล้ววัดค่าจากกล้องจริง พบว่าสาเหตุมีหลายชั้น
ซ้อนกัน:

ชั้นที่ 1 — H.264 DCT Block Artifact

H.264 บีบอัดวิดีโอด้วย Discrete Cosine Transform บนบล็อค 8×8 พิกเซล
ผลคือเมื่อแปลง FFT จะเจอ:
  - Periodic spike ที่ความถี่ตรงกับขนาดบล็อค → ดูเหมือน LCD grid pattern
  - High-frequency noise สูงผิดปกติ → คล้าย screen pixel

วัดค่าจากคนจริงผ่าน RTSP:
    peak_rate  ≈ 0.04887   (สัดส่วน HF pixel ที่เกิน 4σ)
    radial_cov ≈ 1.660     (CoV ของ radial power profile)

แทนค่าในสูตรเดิม:
    spoof_indicator = peak_rate × 25.0 + max(0, radial_cov − 0.7) × 2.0
                    = 0.04887 × 25 + (1.660 − 0.7) × 2
                    = 1.222 + 1.920
                    = 3.142
    score = max(0, 1 − 3.142) = 0.0

→ คนจริงได้ score = 0 ซึ่งต่ำกว่า threshold FFT_SCORE_MIN = 0.130
  → ตัดสินเป็น spoof

ชั้นที่ 2 — Wide-Angle Lens Distortion

IP camera ที่ใช้เป็นเลนส์ wide-angle ทำให้:
  - ขอบโต๊ะ ขอบประตู กรอบรูปบนกำแพง → โค้งบิด → Canny detect เป็น
    "เส้นตรง" หลายเส้น
  - ผู้คนยืนใกล้กล้อง → background features เข้ามาใน margin zone
    → นับเป็น "ขอบจอ"

ชั้นที่ 3 — Bug จากการ Refactor (Day 2026-03-30)

เคยมีรอบหนึ่งที่พยายาม optimize FPS โดยรวม detect() กับ detect_debug()
เป็นฟังก์ชันเดียว แต่:
  - โค้ดเดิมมี early return: if lines is None: return False, 0.0
    → FFT จะถูกตรวจเฉพาะตอนเจอ edge เท่านั้น
  - โค้ดใหม่ลบ early return ออก → FFT รันทุก frame → ค่า variance สูงขึ้น
    → score 0 ค้าง
  - ทำให้ _last_debug cache ค่า 0.000 ตลอดและไม่ refresh เพราะ
    screen_ok = False แล้ว detect() หยุดถูกเรียก

สุดท้าย rollback การ optimize ทั้งหมด (3 ไฟล์: liveness_engine.py,
ui_renderer.py, main.py)


5.4 แนวทางแก้ไขทั้งหมด
--------------------------------------------------------------------------------

A. Re-calibrate FFT Formula

ปรับ baseline ของสูตรให้ tolerate H.264 artifact:

    Parameter            สูตรเดิม    สูตรใหม่    เหตุผล
    ─────────────────────────────────────────────────────────────────────
    peak_rate weight     × 25.0      × 12.0      ลดลงครึ่งหนึ่งเพราะ
                                                  DCT artifact ทำให้
                                                  peak สูงโดยธรรมชาติ
    radial_cov offset    − 0.7       − 1.5       เลื่อน baseline ขึ้น
                                                  ให้ทน compression noise
    radial_cov weight    × 2.0       × 1.0       ลดน้ำหนักเพราะ
                                                  กล้อง IP มีความ
                                                  แปรปรวนสูง

ผลคำนวณใหม่:
    คนจริง RTSP:    0.04887 × 12 + (1.660 − 1.5) × 1
                  = 0.587 + 0.160 = 0.747 → score = 0.253 ✅
    จอมือถือ (คาด): 0.15 × 12 + (2.800 − 1.5) × 1
                  = 1.800 + 1.300 = 3.100 → score = 0.000 ❌

ตอนนี้ score คนจริง = 0.253 > threshold 0.130 → ผ่าน ขณะที่จอมือถือ
ยังโดน reject

B. Time-based Confirmation (กัน flicker)

    SCREEN_CONFIRM_SEC = 3.0   # ต้องเจอ screen ต่อเนื่อง 3 วิถึงจะ fail
    SCREEN_RESET_SEC   = 1.5   # ต้องเจอหน้าจริง 1.5 วิถึงจะ reset counter

ป้องกันกรณี false positive ชั่วครู่ (เช่น คนเอามือบังหน้า, แสงกะพริบ)

C. Margin Zone Tuning

    SCREEN_MARGIN     = 35       # px รอบใบหน้า
    SCREEN_EDGE_MAX   = 0.40     # max edge ratio ใน margin zone
    SCREEN_INNER_MAX  = 0.0110   # max inner density ในพื้นที่หน้า

จำกัดพื้นที่ตรวจให้แคบลง ไม่ครอบคลุม background


5.5 บทเรียนจากปัญหาที่ 5
--------------------------------------------------------------------------------
  1. อย่า hard-code threshold ของ anti-spoofing โดยไม่วัดจากกล้องจริง —
     สูตรที่ใช้ได้กับ webcam อาจพังกับ IP camera เพราะ codec/lens ต่างกัน
  2. Codec มีผลต่อ image processing มากกว่าที่คิด — H.264, MJPEG, H.265
     ต่างสร้าง artifact คนละแบบ
  3. อย่าลบ early return โดยไม่เข้าใจ side effect — early return บางครั้ง
     คือ implicit guard ที่ป้องกัน edge case
  4. คงด่านนี้เปิดอยู่ (SCREEN_DETECT_ENABLED = True) ไม่ปิดทิ้ง เพราะยัง
     มีคุณค่าในการจับ replay attack จริง

6.2 Case A — cuDNN Version Mismatch (เครื่องเรา, Day 2026-03-30)
--------------------------------------------------------------------------------

อาการที่เจอ:

    FPS เมื่อไม่มีหน้า:  20–24 FPS  (ปกติ)
    FPS เมื่อเจอหน้า:    3–6 FPS    (ตกหนัก)
    nvidia-smi:          เห็น process อยู่ (เลยนึกว่า GPU ทำงาน)

การวินิจฉัย:

อ่าน log ละเอียด เจอบรรทัดเล็กๆ:
    2026-03-30 10:23:18 [W:onnxruntime:Default, default_logging_manager.cc:30]
    CUDNN_STATUS_SUBLIBRARY_LOADING_FAILED.
    Falling back to CPUExecutionProvider.

ทุก model (det_10g, 1k3d68, w600k_r50) fallback CPU แบบเงียบๆ
— เป็นแค่ warning ไม่ใช่ error

ตรวจ version stack:

    $ pip show onnxruntime-gpu | grep Version
    Version: 1.20.1

    $ nvcc --version | grep release
    Cuda compilation tools, release 12.6

    $ pip show nvidia-cudnn-cu12 | grep Version
    Version: 9.10.2     ← ปัญหาอยู่ตรงนี้

สาเหตุที่แท้จริง:

onnxruntime-gpu 1.20.1 ถูก compile กับ cuDNN frontend version 1.7.0 ซึ่งรู้จัก
เฉพาะ cuDNN sub-library API ที่มาก่อน v9.6 แต่ nvidia-cudnn-cu12 9.10.2
ออกหลังจากนั้นและ:
  - ปรับ ABI ของบาง sub-library
  - เพิ่ม sub-library ใหม่ที่ frontend เก่าไม่รู้จัก
  - ทำให้ตอน load runtime พบ symbol resolution failure
    → return CUDNN_STATUS_SUBLIBRARY_LOADING_FAILED

วิธีแก้:

    pip install "nvidia-cudnn-cu12==9.5.1.17" --force-reinstall

เลือก 9.5.1.17 เพราะอยู่ในช่วงที่ onnxruntime-gpu 1.20.1 build รองรับ
(9.4–9.5)

ผลลัพธ์หลังแก้:

    2026-03-30 14:45:02 [I:onnxruntime] CUDAExecutionProvider initialized
    [ORT] Using: ['CUDAExecutionProvider', 'CPUExecutionProvider']
    FPS: 22–25 (เจอหน้าก็ยังคงประมาณนี้)

ทั้ง 3 model โหลดบน GPU สำเร็จ — ไม่มี "Falling back to CPU" อีก


6.3 Case B — Segmentation Fault Exit -11 (จากทีม, Docker)
--------------------------------------------------------------------------------
ทีมเจอบนสภาพแวดล้อมต่าง:
  - Container: serverapi (Docker)
  - GPU: RTX 3050
  - อาการ: Crash ทันทีตอน app.prepare() — Exit code -11 (SIGSEGV)
    ไม่มี Python traceback ชัดเจน

ปัญหานี้รุนแรงกว่าของเราเพราะ process ตายทันที ไม่ใช่แค่ fallback CPU
การ debug ยากกว่ามากเพราะ Python ไม่ได้ raise exception
— เป็น native crash ระดับ binary

สาเหตุ 3 ชั้นที่ซ้อนทับกัน:

ชั้น Software — Dependency Conflict

ตอน build container, pip ดึง latest version ของทุก library อัตโนมัติ:

    Library              เวอร์ชันที่ pip ดึง   ปัญหา
    ─────────────────────────────────────────────────────────────────────
    numpy                2.x                   NumPy 2.0 break ABI ของ
                                                NumPy 1.x — onnx, opencv,
                                                insightface ที่ build กับ
                                                1.x ใช้ไม่ได้
    protobuf             7.x                   ABI break กับ
                                                onnx/onnxruntime ที่ใช้
                                                protobuf 3.x/4.x
    opencv-python        4.13                  ABI ใหม่ไม่เข้ากับ
                                                insightface เวอร์ชันเก่า

ผลคือเมื่อ Python import insightface แล้วเรียก native code ของมันที่ link
กับ _numpy_api_v1.so (เก่า) แต่ runtime กลับโหลด _numpy_api_v2.so (ใหม่)
→ symbol mismatch → SIGSEGV

ชั้น Infrastructure — Container ไม่ Mount GPU

docker-compose.yml ของ container serverapi ไม่มี config สำหรับ GPU
ดังนั้น:
  - ภายใน container: ไม่มี /dev/nvidia* device
  - แต่ pip install onnxruntime-gpu (ไม่ใช่ onnxruntime ตัว CPU)
  - ตอน FaceAnalysis(name="buffalo_l") → onnxruntime พยายาม initialize
    CUDA context → เรียก driver ที่ไม่มี → SIGSEGV

วิธีดูว่า container เห็น GPU หรือเปล่า:

    docker exec serverapi nvidia-smi
    # ถ้า command not found หรือ "No devices were found" = ไม่ได้ mount

ชั้น Data — Model Race Condition

เริ่มระบบด้วย 2 กล้องพร้อมกัน → spawn 2 thread → ทั้ง 2 เรียก
FaceAnalysis(name="buffalo_l") พร้อมกัน → ทั้งคู่เช็คพบว่า
~/.insightface/models/buffalo_l/ ยังไม่มี → เริ่ม download โมเดลพร้อมกัน
→ เขียนไฟล์เดียวกันทับซ้อน → ไฟล์ .onnx corrupt

ครั้งต่อมาที่รัน → onnxruntime พยายาม parse .onnx ที่เสีย → SIGSEGV

แนวทางแก้ครบทั้ง 3 ชั้น:

A. Clean Environment

    # 1. ลบ library ที่มีปัญหา
    pip uninstall numpy protobuf opencv-python opencv-contrib-python -y

    # 2. ลบโมเดลที่ corrupt
    rm -rf ~/.insightface/models/buffalo_l/

B. Pin Stable Stack ใน requirements.txt

    # Pin version เพื่อป้องกัน auto-upgrade
    numpy<2.0.0
    protobuf<5.0.0
    opencv-python<4.10
    opencv-contrib-python<4.10
    onnxruntime-gpu==1.20.1
    nvidia-cudnn-cu12==9.5.1.17
    insightface==0.7.3

C. เปิด GPU ให้ Container

แก้ docker-compose.yml:

    services:
      serverapi:
        image: facereg-api:latest
        deploy:
          resources:
            reservations:
              devices:
                - driver: nvidia
                  count: all
                  capabilities: [gpu]
        runtime: nvidia              # สำหรับ docker-compose v1
        environment:
          - NVIDIA_VISIBLE_DEVICES=all
          - NVIDIA_DRIVER_CAPABILITIES=compute,utility

ตรวจหลัง up ใหม่:

    docker exec serverapi python -c \
        "import onnxruntime; print(onnxruntime.get_available_providers())"
    # ต้องเห็น: ['CUDAExecutionProvider', 'CPUExecutionProvider']

D. Atomic Model Initialization

แก้ flow ตอน startup:

    # ❌ เดิม — race เพราะ 2 thread เริ่มพร้อมกัน
    for cam in cameras:
        threading.Thread(target=run_camera, args=(cam,)).start()
        # run_camera() ข้างในเรียก FaceAnalysis() → race ตอน download

    # ✅ ใหม่ — warm-up ใน main thread ก่อน spawn
    print("[INIT] Warming up InsightFace model...")
    warm_app = FaceAnalysis(name="buffalo_l", providers=use_providers)
    warm_app.prepare(ctx_id=0, det_size=cfg.DET_SIZE)
    del warm_app  # download/cache เสร็จแล้ว ปล่อย GPU memory
    print("[INIT] Model ready, spawning workers")

    for cam in cameras:
        threading.Thread(target=run_camera, args=(cam,)).start()
        # ตอนนี้ทุก thread เจอ cache อยู่แล้ว — ไม่มี race

หรือใช้ filelock lock ระหว่าง download:

    from filelock import FileLock
    with FileLock(os.path.expanduser("~/.insightface/buffalo_l.lock")):
        app = FaceAnalysis(name="buffalo_l", ...)


6.4 ของป้องกัน (Defensive Code) ที่ใส่ไว้ใน main.py
--------------------------------------------------------------------------------
ดู main.py:391-414:

    import onnxruntime as ort
    available = ort.get_available_providers()
    use_providers = [p for p in available if p != "TensorrtExecutionProvider"]
    print(f"[ORT] Using: {use_providers}")    # ← log สิ่งที่ใช้จริง

    try:
        app = FaceAnalysis(name="buffalo_l", providers=use_providers, ...)
    except Exception as e:
        print(f"[WARN] GPU ใช้ไม่ได้: {e}")
        print("[WARN] Fallback → CPU")
        app = FaceAnalysis(name="buffalo_l",
                          providers=["CPUExecutionProvider"], ...)

หลักการคือ:
  - Print providers ที่ใช้จริง — ถ้าไม่มี CUDAExecutionProvider ผู้ใช้
    เห็นทันที
  - Try/except + ชัดเจน — ถ้า GPU พังต้อง print warning ดังๆ ไม่ใช่ silent
  - แต่ก็ยังให้ระบบรันต่อบน CPU — เพื่อ degrade gracefully


6.5 บทเรียนเรื่อง GPU (สำคัญที่สุดในโปรเจกต์นี้)
--------------------------------------------------------------------------------

  1. Silent fallback คือศัตรูตัวจริง — ML library ส่วนใหญ่ออกแบบมาให้
     "ทำงานต่อได้" ตอน GPU พัง แต่นั่นทำให้ผู้ใช้ไม่รู้ว่ามีปัญหา
     ต้อง log providers ที่ active จริงเสมอ

  2. Version Matrix สำคัญกว่าที่คิด

         onnxruntime-gpu 1.20.1  ⟷  CUDA 12.x  ⟷  cuDNN 9.4–9.5
                                 ⟷  driver ≥ 525

     ระบบ ML stack คือ chain of dependencies ที่ทุกตัวต้อง compatible กัน
     — pip auto-upgrade คือศัตรู

  3. 3 ชั้นของปัญหา GPU ต้องเช็คครบ:

         ชั้น              สิ่งที่เช็ค                 คำสั่งตรวจ
         ───────────────────────────────────────────────────────────────
         Software          Library version,           pip list | grep -E
                           ABI compatibility           'numpy|onnx|opencv'
         Infrastructure    Driver, CUDA, cuDNN,       nvidia-smi,
                           container GPU mount         nvcc --version
         Data              Model file integrity,      md5sum
                           race condition              ~/.insightface/
                                                       models/*.onnx

  4. Race condition ของ model download — multi-thread/multi-process ต้องมี
     lock หรือ pre-warm — ห้ามให้หลาย worker download model พร้อมกัน

  5. nvidia-smi ไม่ใช่หลักฐานว่า GPU ทำงาน — มันแค่บอกว่าเห็น GPU
     มี process อยู่ แต่อาจเป็นแค่ CUDA context ที่โหลดเปล่าๆ ต้องดู
     FPS จริงและ log ของ onnxruntime คู่กัน

  6. Pin version ใน requirements.txt — อย่าเขียนแค่ onnxruntime-gpu
     ต้อง onnxruntime-gpu==1.20.1 ถ้าไม่ pin วันหนึ่ง CI build ใหม่
     → ดึง version ใหม่ → พังโดยไม่รู้ตัว

  7. Container ต้อง mount GPU เป็นพิเศษ — Docker by default ไม่เห็น GPU
     ต้องใช้ nvidia-container-toolkit + config
     deploy.resources.reservations.devices ใน docker-compose

7.1 สถานะก่อน Migrate
--------------------------------------------------------------------------------
ก่อน v5 ระบบใช้ face_recognition library ซึ่งเบื้องหลังคือ dlib ResNet ที่:

  - ขนาด embedding: 128 dimensions
  - Loss function: Triplet loss
  - Training set: face_recognition_models (เน้น face คนผิวขาว)
  - Distance metric: Euclidean distance
  - Threshold default: ~0.6 (lower = stricter)
  - ความเร็ว: CPU-only (ไม่มี GPU support ใน face_recognition wrapper)

ปัญหาที่ทำให้ต้อง migrate:

  1. Accuracy ต่ำกับใบหน้าคนเอเชีย — Training set bias ของ dlib ทำให้:
     - คนเอเชียหน้าคล้ายๆ กันมักจะถูกจำสลับตัว
     - คนเดียวกันแต่มุมหน้าเปลี่ยน (ก้ม/เงย/ตะแคง) → distance สูงเกิน
       threshold
     - แสงน้อย → embedding noisy → recognition ล้มเหลว

  2. ไม่ใช้ GPU — face_recognition wrapper เรียก dlib ผ่าน CPU เท่านั้น
     แม้ระบบจะมีการ์ด NVIDIA → ใช้งาน hardware ไม่เต็ม

  3. Pipeline ช้า — แต่ละเฟรมใช้ ~150ms รวม detect + encode
     → FPS = 6-8 → ทำ multi-cam ไม่ได้


7.2 การ Migrate สู่ ArcFace
--------------------------------------------------------------------------------
ย้ายมาใช้ InsightFace buffalo_l model pack ที่มี:

  - Backbone: ResNet50 (w600k_r50.onnx)
  - Loss function: ArcFace (additive angular margin loss)
  - ขนาด embedding: 512 dimensions
  - Training set: WebFace600K (ใหญ่กว่ามาก, ครอบคลุมทุก ethnicity)
  - Distance metric: Cosine similarity
  - Runtime: ONNX Runtime + GPU acceleration

ดู encode_faces_arcface.py:55 และ main.py:400:

    app = FaceAnalysis(name="buffalo_l", providers=use_providers)
    app.prepare(ctx_id=0, det_size=(640, 640))


7.3 สิ่งที่ต้องเปลี่ยน Domino Effect
--------------------------------------------------------------------------------
การเปลี่ยน face recognition backbone ไม่ใช่แค่ swap library
มันคือ data migration ทั้งระบบ:

A. Embedding ทั้งหมดเก่าเป็นโมฆะ

  - ไฟล์ encodings.pkl (128d) ใช้ไม่ได้ → ต้อง re-encode ทุกคนใหม่
  - รัน python encode_faces_arcface.py --dir known_faces/ ทุกครั้งที่
    เปลี่ยน backbone
  - ขนาดไฟล์ใหญ่ขึ้น ~4 เท่า (128 floats → 512 floats per person)

B. Distance Metric เปลี่ยน

ดู main.py:219-228:

    # ─── Face Matching (cosine similarity) ──────
    def match_face(emb_512d, known_norms, known_names):
        """เทียบ 512d embedding กับฐานข้อมูล ด้วย cosine similarity"""
        emb_norm = emb_512d / (np.linalg.norm(emb_512d) + 1e-10)
        sims = known_norms @ emb_norm           # cosine similarity 0..1
        best_idx = np.argmax(sims)
        if sims[best_idx] >= cfg.FACE_TOLERANCE:  # 0.35
            return known_names[best_idx], sims[best_idx]
        return None, sims[best_idx]

หลักการเปลี่ยนใหม่:
  - Normalize embedding ทั้ง query และ database (/= norm)
  - Vectorized matrix multiplication เทียบกับทุกคนพร้อมกัน
  - Higher = more similar (กลับด้านจากเดิมที่ Euclidean: lower = more similar)

C. Threshold ต้อง Re-tune

    # config.py:18
    FACE_TOLERANCE = 0.35   # cosine similarity ขั้นต่ำ (ArcFace ใช้ 0.3-0.4)

  - ArcFace cosine similarity: คนเดียวกัน ~0.5-0.8, คนต่างกัน ~0.0-0.3
  - ตั้ง 0.35 = สมดุลระหว่าง false accept กับ false reject
  - ก่อนตั้งค่านี้ต้อง measure จริงกับ dataset ของ known_faces เอง

D. Anti-Spoofing Threshold ก็ต้อง Re-tune

ดู config.py:120:

    MOTION_VAR_MIN = 1.2  # ปรับเพราะ ArcFace ใช้ full-res landmarks
                          # (เดิม 0.3 ที่ 0.25x)

เพราะ ArcFace pipeline ใช้ landmark resolution ต่างกันจาก face_recognition
(full-res vs downsampled 0.25x) → magnitude ของ motion variance ต่างกัน
4 เท่า

E. Hardware Requirement เปลี่ยน

  - เพิ่ม: ต้องมี NVIDIA GPU + CUDA + cuDNN + onnxruntime-gpu
  - เพิ่ม: ต้อง download buffalo_l model (~250 MB) ครั้งแรก
  - ผลพลอย: เกิดปัญหาในข้อ 6 ตามมา (cuDNN mismatch, race condition)

7.5 บทเรียนจากการ Migrate
--------------------------------------------------------------------------------

  1. Face recognition backbone migration คือ breaking change ทั้งระบบ —
     ต้องเตรียม:
     - Re-encode dataset ทั้งหมด
     - Re-tune threshold ทั้งหมด (matching + anti-spoofing)
     - เปลี่ยน distance metric → ระวัง logic เปรียบเทียบกลับด้าน
     - อัปเดต hardware stack

  2. ขนาด embedding ที่ต่างกัน = format ต่างกัน — encodings.pkl เก่าใช้
     ไม่ได้เลย ต้องมี migration script + ลบของเก่าทิ้งให้สะอาด ไม่งั้น
     load ปนกันแล้ว shape mismatch

  3. อย่า migrate โดยไม่วัด baseline — ถ้าไม่มี dataset test ก่อน/หลัง
     จะไม่รู้ว่ามันดีขึ้นจริงไหม → ก่อน migrate ควรเก็บภาพ test set ไว้
     run ทั้ง 2 model เปรียบเทียบ

  4. การ migrate อาจสร้างปัญหาใหม่ — ArcFace ที่หนักขึ้น → ต้อง GPU
     → เกิดปัญหา GPU stack (ข้อ 6) → ต้อง debug ต่อ ปัญหาเหล่านี้คือ
     technical debt ที่หลีกเลี่ยงไม่ได้ในการ upgrade

  5. คงเก็บ encode_faces_arcface.py ไว้ — เพราะ workflow การเพิ่มคนใหม่
     ต้องรัน script นี้เพื่อ re-encode ทั้ง pkl ใหม่ → เป็น operational
     tool ที่ขาดไม่ได้
