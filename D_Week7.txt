1. แก้ปัญหา Loading Overlay ค้างบนหน้ากล้อง (CameraView.vue)
   ─────────────────────────────────────────────────────────────────
   เดิม loading overlay ("กำลังดาวน์โหลด...") แสดงค้างอยู่ตลอด
   แม้กล้องจะเชื่อมต่อสำเร็จและ stream กำลังทำงานปกติ

   สาเหตุ — Vue 3 v-else binding rule
     ในการแก้ไข z-index ครั้งก่อน มีการย้าย hover highlight div
     ไปวางระหว่าง <img v-if="..."> และ <div v-else>
     Vue 3 กำหนดว่า v-else ต้องอยู่ติดกับ v-if โดยไม่มี element คั่น
     เมื่อมี hover div คั่น v-else จึงไปจับคู่กับ v-if="isThumbnail()"
     ที่อยู่ถัดมาแทน ทำให้ fallback overlay แสดงตลอดเวลาสำหรับ
     กล้อง main/focused โดยไม่สนว่า stream จะ live หรือไม่

   แก้ไข:
     - ย้าย hover highlight divs ทั้งสองตัวไปวางหลัง </div> ปิด v-else block
     - ให้ <img v-if> กับ <div v-else> อยู่ติดกันไม่มีอะไรคั่น
     - ลำดับ DOM ใหม่: img (v-if) → fallback (v-else) → hover overlay

2. ปรับปรุง Dashboard หน้าภาพรวม — เพิ่ม 2 Section แยกรายชื่อ

     - PersonCard ใช้ photoMode="profile"

3. ปรับปรุง Camera Grid Layout — จัดเรียงกล้องอัตโนมัติ
   ─────────────────────────────────────────────────────────────────
   เดิมการแสดงผลกล้องใช้ GRID_COLS=3 ตายตัว ทำให้:
     - 4 กล้อง: 3+1 (กล้องสุดท้ายกว้างแค่ 1/3 มีพื้นที่ว่าง 2/3)
     - 5 กล้อง: 3+2 (แถวล่างกว้างแค่ 1/3 ต่อกล้อง)
     - 7 กล้อง: 3+3+1 (กล้องสุดท้ายกว้างแค่ 1/3)
     - 8 กล้อง: 3+3+2 (แถวล่างไม่เต็ม)
   ทำให้ layout ไม่สวยงามและไม่ใช้พื้นที่ให้เต็มประสิทธิภาพ

   แก้ไข:
   - เพิ่ม getGridCols(n) function คำนวณ columns ที่เหมาะสมตามจำนวนกล้อง:
       1 กล้อง → 1 col   (1×1 เต็มจอ)
       2 กล้อง → 2 cols  (2×1 เคียงข้าง)
       3 กล้อง → 3 cols  (3×1 แถวเดียว)
       4 กล้อง → 2 cols  (2×2 สี่เหลี่ยม)
       5–6    → 3 cols  (3×2)
       7–8    → 4 cols  (4×2)
       9      → 3 cols  (3×3)

   - แก้ cameraStyle() ให้กล้องในแถวสุดท้ายยืดเต็มแถวเสมอ:
       คำนวณ lastRowN = n % cols (จำนวนกล้องในแถวสุดท้าย)
       ถ้าเป็นแถวสุดท้าย: ใช้ lastRowN เป็น effCols แทน cols
       ทำให้ 5 กล้อง → แถวล่าง 2 กล้อง แต่ละตัวกว้าง 50% (เต็มแถว)
       7 กล้อง → แถวล่าง 3 กล้อง แต่ละตัวกว้าง 33.3% (เต็มแถว)

   - แก้ feedMinHeight ให้ใช้ getGridCols() แทน logic เดิม

■ งานที่ดำเนินการในวันนี้
────────────────────────────────────────────────────────────────────────

1. ย้ายสภาพแวดล้อมการพัฒนาจาก Ubuntu มายัง macOS (Apple Silicon)
   ─────────────────────────────────────────────────────────────────
   เปลี่ยนเครื่องพัฒนาจาก Ubuntu (Linux + NVIDIA GPU) มาเป็น MacBook
   (macOS + Apple Silicon ARM) ทำให้ต้องตั้งค่า environment ใหม่ทั้งหมด

   ปัญหาที่พบระหว่างติดตั้ง Python packages:
     - CUDA/NVIDIA packages (cuda-bindings, nvidia-*, triton) ไม่รองรับ macOS
       → กรองออกและแทน onnxruntime-gpu ด้วย onnxruntime (CPU)
     - torch+cu126 / torchvision+cu126 ไม่มี wheel สำหรับ macOS
       → ใช้ torch / torchvision เวอร์ชัน CPU แทน
     - numpy==1.26.4 ขัดกับ opencv-python 4.13 ที่ต้องการ numpy>=2
       → ปลด version pin ให้ uv resolver เลือกเอง
     - tensorflow==2.16.2 ต้องการ ml-dtypes~=0.3.1 แต่ jax==0.7.1,
       keras==3.13.2, onnx==1.20.1 ต้องการ ml-dtypes>=0.5.0
       → ปลด version pin ของ tensorflow/keras/onnx/ml_dtypes ทั้งหมด
     - dlib==20.0.0 build ไม่ได้บน macOS SDK ใหม่ (fp.h not found)
       → ตัด dlib และ face_recognition ออก
         (โปรเจคใช้ InsightFace ไม่ใช้ face_recognition library)
     - pip resolver แก้ conflict ไม่ได้ → เปลี่ยนมาใช้ uv แทน
       → ติดตั้งสำเร็จ 136 packages

2. ทดสอบรันระบบบน macOS — วิเคราะห์ปัญหาที่พบ
   ─────────────────────────────────────────────────────────────────
   ทดสอบรัน main.py และ uvicorn api:app พบปัญหาตามลำดับ:

   ปัญหาที่ 1 — EXTERNAL_API_URL ไม่ได้ตั้งค่า
     api_client.py อ่าน os.environ["EXTERNAL_API_URL"] โดยตรง (ไม่มี default)
     เมื่อไม่มีไฟล์ .env → KeyError ทันทีตอน import
     แนวทาง: สร้าง .env หรือเปิด MOCK_MODE = True ใน api_client.py

   ปัญหาที่ 2 — db_config.json ไม่มีในเครื่องใหม่
     db.py พยายาม open("db_config.json") เมื่อไม่มี DB_HOST env var
     ไฟล์นี้อยู่ใน .gitignore จึงไม่ถูก commit ตามมาด้วย
     แนวทาง: สร้างไฟล์ใหม่หรือใช้ DB_HOST env var แทน

   ปัญหาที่ 3 — PostgreSQL ไม่ได้ติดตั้ง และไม่มี Homebrew
     ระบบใช้ PostgreSQL ผ่าน psycopg ไม่ใช่ SQLite
     macOS ใหม่ไม่มีทั้ง Homebrew และ PostgreSQL

3. วิเคราะห์แนวทางรันระบบผ่าน Docker บน macOS
   ─────────────────────────────────────────────────────────────────
   ตรวจสอบพบว่า:
     - Docker Desktop ติดตั้งอยู่แล้ว (Docker version 29.4.1)
     - Image photcharap/face-attendance:latest push ไว้บน Docker Hub แล้ว
     - docker/ โฟลเดอร์อยู่ใน .gitignore จึงไม่มีในเครื่องใหม่

   แนวทาง: pull image จาก Docker Hub และสร้าง docker-compose.yml ใหม่
     ข้อดี — ไม่ต้องติดตั้ง PostgreSQL / Homebrew แยก
             ใช้ environment เดียวกับ production บน Ubuntu

   การซ่อมรอบที่สอง:
     - แกะเครื่องอีกครั้งและตรวจสอบอย่างละเอียด
     - พบคราบสกปรกเล็กน้อยบนหน้าแผงสัมผัสของ SSD/RAM
     - พี่ที่กองงานสนับสนุนแนะนำให้ใช้กระดาษทรายขัดหน้าแผงสัมผัส
       เพื่อกำจัดคราบออกไซด์และสิ่งสกปรก
     - ประกอบกลับและทดสอบอย่างละเอียด — เครื่องทำงานได้ตามปกติ

2. ซ่อมเครื่องคอมพิวเตอร์ All-in-One เครื่องที่ 2 — อัปเกรดพื้นที่จัดเก็บ
   ─────────────────────────────────────────────────────────────────
   ช่วงบ่าย รับเครื่องคอมพิวเตอร์ All-in-One อีกหนึ่งเครื่องเข้ามา
   ด้วยคำร้องขอการอัปเกรดพื้นที่จัดเก็บและทำความสะอาดภายในเครื่อง

   ระหว่างประกอบกลับหลังอัปเกรด พบปัญหาเพิ่มเติม:
     - เครื่องเปิดไม่ติดเมื่อปิดฝาหลัง
     - ตรวจสอบอย่างละเอียดพบว่าตัวชิป CPU มีอาการช็อต
       และเกิดรอยไหม้ 2 จุดบนตัวชิป
     - พี่ในกองพิจารณาแล้วว่าความเสียหายที่ CPU อยู่ในระดับที่
       ไม่สามารถซ่อมต่อไปได้

  - Contact Pad Cleaning — การใช้กระดาษทรายขัดหน้าแผงสัมผัสเพื่อกำจัดออกไซด์

■ ปัญหาที่พบและแนวทางแก้ไข
────────────────────────────────────────────────────────────────────────

  ปัญหา : เครื่อง All-in-One อ่าน SSD ไม่ได้ แม้หลังทำความสะอาดแล้ว
           ปัญหายังกลับมาซ้ำหลังใช้งาน 3–4 ครั้ง
  วิเคราะห์: คราบออกไซด์หรือสิ่งสกปรกบนหน้าแผงสัมผัสของ SSD/RAM
             ทำให้การสัมผัสไม่ดีและเกิดการเชื่อมต่อที่ไม่เสถียร
             การเช็ดธรรมดาไม่สามารถกำจัดออกไซด์ได้หมด
  แก้ไข : ใช้กระดาษทรายขัดหน้าแผงสัมผัสเพื่อกำจัดออกไซด์
           ทำให้การสัมผัสดีขึ้นและเครื่องทำงานได้ตามปกติ

  ปัญหา : เครื่อง All-in-One เครื่องที่ 2 เปิดไม่ติดเมื่อปิดฝาหลัง
           ตรวจพบรอยไหม้ 2 จุดที่ตัวชิป CPU
  วิเคราะห์: ตัวชิป CPU มีอาการช็อตและเกิดความเสียหายถาวร
             ความเสียหายเกินกว่าการซ่อมบำรุงปกติจะทำได้
  แก้ไข : พิจารณาแล้วว่าไม่สามารถซ่อมต่อไปได้ เนื่องจาก CPU เสียหายถาวร
